تُباع معظم أدوات سطح المكتب البعيد بطريقة واحدة: اشتراك سحابي تتولى فيه خوادم المورّد تنسيق الجلسات وترحيلها حين يتعذر المسار المباشر. أما الاستضافة الذاتية فتنقل هذه الأدوار إلى بنية تحتية تتحكم بها: تنسّق العملاء اتصالاتها عبر خادم المعرّف/الالتقاء (ID/rendezvous) الخاص بك، وتتصل مباشرةً متى أمكن، وتلجأ إلى خادم الترحيل (relay) الخاص بك عند الحاجة. يعرض هذا المقال حجة هذا النموذج، مستخدمًا RustDesk Server OSS (خادم المجتمع المجاني) وServer Pro مثالًا ملموسًا.

## ما الذي تعنيه فعليًا «الاستضافة الذاتية لسطح المكتب البعيد»

ثمن الراحة التي توفرها السحابة وحدها أن قائمة أجهزتك، والبيانات الوصفية لاتصالاتك، وأحيانًا حركة جلساتك، تمر عبر طرف ثالث، رهنًا بجاهزيته وتسعيره ووضعه الأمني.

والاستضافة الذاتية تقلب هذه المعادلة. فمع RustDesk يشغّل فريقك خدمتَي المعرّف/الالتقاء والترحيل، ويضع Server Pro أيضًا لوحة تحكم الويب وبيانات الأجهزة المخزَّنة على بنيتك التحتية. وتتدفق الجلسات المباشرة بين نقاط النهاية، بينما تستخدم الجلسات المُرحَّلة خادم الترحيل الخاص بك. **عميل RustDesk وServer OSS [مرخَّصان بموجب AGPL](https://github.com/rustdesk/rustdesk)**؛ **أما Server Pro فمنتج تجاري مغلق المصدر تستضيفه بنفسك**.

## السحابة وحدها مقابل الاستضافة الذاتية: نظرة سريعة

| | أداة سحابية نموذجية | ذاتي الاستضافة (RustDesk Server Pro) |
| --- | --- | --- |
| أين تجري وساطة الجلسات | سحابة المورّد | جهازك في مقرك أو خادم VPS خاص بك |
| إقامة البيانات | يتحكم بها المورّد | تعمل خدمات جانب الخادم على بنية تحتية تتحكم بها؛ و[مسارات نقاط النهاية تظل مهمة](/ar/blog/remote-desktop-data-sovereignty-gdpr-ar) |
| الاتصالات/القنوات المتزامنة المرخَّصة | حصة تعتمد على الخطة | غير محدودة في الخطط القياسية؛ ولخطة Customized V2 حصة مرخَّصة |
| نموذج التسعير | مستخدمون ونقاط نهاية وحصص اتصال بحسب كل منتج | [مستخدمو تسجيل الدخول والأجهزة المُدارة](https://rustdesk.com/pricing)؛ وترخّص Customized V2 التزامن أيضًا |

| من يشغّل الخادم | المورّد | أنت |

ولا تكلّفك الاستضافة الذاتية شيئًا من القدرات. فلـ[مزوّدي الخدمات المُدارة](/ar/blog/rustdesk-for-msps-ar) وفرق تقنية المعلومات الداخلية، يضيف Server Pro لوحة تحكم ويب ذاتية الاستضافة مع [التحكم في الوصول](https://rustdesk.com/docs/en/self-host/rustdesk-server-pro/permissions/) لكل مستخدم ومجموعة أجهزة، إضافة إلى مولّد العملاء المخصصة و[تسجيل الدخول الموحّد عبر LDAP/OIDC](https://rustdesk.com/docs/en/self-host/rustdesk-server-pro/ldap/) من خطة Basic. ولا تكلّفك شيئًا من قابلية التوسع: فقد سجّل الخادم العام لـ RustDesk أكثر من مليوني نقطة نهاية متصلة على مضيف واحد بـ 12 نواة وذاكرة 32 جيجابايت في 7 يوليو 2026 (قياس داخلي)، ويغطي [دليل تخطيط الأساطيل الكبيرة](/ar/blog/rustdesk-scale-50000-200000-devices-ar) ما يجب اختباره في Server Pro.

## ما الذي يتطلبه فعليًا تشغيل الخادم

يأتي التحكم مع عمل تشغيلي: إعداد أولي لمرة واحدة، ثم صيانة روتينية. وإليك القائمة الملموسة:

- **جهّز مضيفًا.** متطلبات العتاد في RustDesk منخفضة، لذا تكفي آلة Linux افتراضية متواضعة، في مقرك أو على خادم VPS رخيص، لتشغيل خدمتَي المعرّف/الالتقاء والترحيل. حدّد حجمها بحسب عدد أجهزتك ومقدار الحركة التي تمر عبر الترحيل بدلًا من الاتصال المباشر (peer-to-peer).
- **افتح المنافذ التي تستخدمها فقط.** تحتاج عملاء RustDesk الأصلية إلى المنافذ **TCP 21115-21117 وUDP 21116** لاختبار NAT وخدمات الاتصال والتسجيل ونبضات الاتصال (heartbeat) والترحيل. لا تكشف نطاق المنافذ 21114-21119 بأكمله: فالمنفذان TCP 21118-21119 لخدمات WebSocket الخلفية، والمنفذ TCP 21114 للواجهة الخلفية لـ HTTP API ولوحة التحكم في Pro. وحين يوضع وكيل عكسي HTTPS/WSS أمام واجهة Pro البرمجية وخدمات WebSocket، اكشف المنفذ TCP 443 وحده للعامة لهذه الحركة، وأبقِ المنفذ 21114 والمنفذين 21118-21119 داخليين. والمنفذ 443 العام لا يغني عن المنافذ الأساسية للعملاء الأصلية إذا كانت تتصل أيضًا. راجع [مرجع المنافذ الرسمي](https://rustdesk.com/docs/en/self-host/).
- **أعدّ TLS.** أنهِ اتصالات HTTPS وWSS عند الوكيل العكسي، كي تستخدم بيانات الاعتماد واستدعاءات API وحركة عميل المتصفح المنفذ العام TCP 443، بدلًا من كشف لوحة التحكم/API عبر HTTP غير المشفّر أو خدمات WebSocket الخلفية الخام.
- **انسخ احتياطيًا.** يحتفظ الخادم بقائمة أجهزتك وحسابات المستخدمين ودفتر العناوين وقواعد الوصول. جدوِل نسخًا احتياطية، واختبر فعلًا أنك تستطيع الاستعادة منها.
- **التزم بوتيرة للتحديثات.** تصدر إصدارات جديدة من الخادم بمرور الوقت، وأنت المسؤول عن نظام التشغيل تحتها. حدّد من يطبّق التحديثات وكم مرة.
- **راقبه.** أصبحت خدمة التنسيق ملكك، لذا تراقب الجاهزية ومساحة القرص ومعدل نقل الترحيل، وتتولى التنبيهات والتعافي.

لا شيء من هذا غريب على فريق يشغّل خوادم Linux بالفعل. عيّن مسؤولًا وجدولًا للتحديثات والنسخ الاحتياطي وتجديد الشهادات واختبارات الاستعادة، فيعمل الخادم كأي بنية تحتية روتينية.

## كيف تقيّم الاستضافة الذاتية

- **ابدأ بـ Server OSS.** انشره بعد ظهر اليوم، وافحص شيفرته، وشغّله ما شئت: لا رسوم ترخيص ولا تاريخ انتهاء، وإنما تكاليف الاستضافة وعرض النطاق الخاصة بك فقط.
- **هل تحتاج إلى ميزات Pro؟** أسعار الخطط الحالية متوفرة على [rustdesk.com/pricing](https://rustdesk.com/pricing)، ويستطيع [sales@rustdesk.com](mailto:sales@rustdesk.com) إخبارك بخيارات التقييم المتاحة حاليًا.
- **تفضّل المشاهدة على التثبيت؟** يتوفر عرض توضيحي كامل بالفيديو على [قناة RustDesk على YouTube](https://www.youtube.com/@rustdesk).

إذا كانت تغييرات الأسعار، أو الشيفرة المغلقة، أو سحابة المورّد هي ما دفعك للبحث، فالاستضافة الذاتية هي الحل البنيوي لا مجرد خصم: أنت من يختار مكان تشغيل الخوادم ومن يشغّلها. وبالنسبة لفريق يشغّل بنيته التحتية بالفعل، فهي خطوة تالية لا قفزة: جرّب على Server OSS، وقدّر سعة الترحيل لذروة جلساتك، ثم انقل الأسطول حين يثبت سير العمل.
