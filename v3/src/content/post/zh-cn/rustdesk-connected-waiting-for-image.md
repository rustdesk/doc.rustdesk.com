如果 RustDesk 显示 **“已连接，等待画面传输”**，随后出现黑屏，最难的部分其实已经成功了：两端已经找到彼此，会话也已建立。缺的只是 _画面_。最常见的情况是远程机器上没有可捕获的画面；少数情况下，是编解码器、GPU 驱动或中继路径让视频流卡住了。本文从最常见的原因讲到边缘情况，并为每种原因给出具体的修复方法。

## 简短回答

会话已经连上，但画面没有传过来。最常见的原因是远程机器上没有可捕获的画面：**没有接显示器、显示器处于休眠状态，或缺少屏幕录制权限**。给 RustDesk 提供一个真实且处于唤醒状态的显示器（实体显示器、HDMI 仿真插头或虚拟显示器）和正确的权限；如果画面仍未出现，再切换到 VP9 等其他编解码器。如果依然黑屏，请更新 GPU 驱动，并检查中继端口是否可达。

## 从这里开始：有没有可以捕获的画面？

最常见的原因是**无头主机**——服务器、迷你电脑或工作站在没有连接显示器的情况下运行，或者显示器已经休眠。没有活动显示器时，往往也就没有可捕获的帧缓冲区，于是 RustDesk 能连上，却没有内容可发送。这种情况在 RustDesk 的问题跟踪中反复出现，包括[目标机器显示器关闭时出现黑屏的报告](https://github.com/rustdesk/rustdesk/issues/9884)，以及长期存在的[“Connected, waiting for image”讨论帖](https://github.com/rustdesk/rustdesk/issues/222)。

有两种办法给它提供可捕获的画面：

- **接上显示器**，并确保它已通电且处于唤醒状态。
- **使用 HDMI（或 DisplayPort）仿真插头。** 这类廉价适配器能让 GPU 以为已连接显示器，从而持续渲染帧缓冲区供 RustDesk 捕获。这是解决无头台式机和家用服务器问题的标准做法。

如果显示器 _确实_ 接着，那么下一个怀疑对象就是它进入了休眠。

## 按原因修复

| 原因                  | 表现                   | 修复方法                                                                                       |
| --------------------- | ---------------------- | ---------------------------------------------------------------------------------------------- |
| 无头主机 / 无显示器   | 服务器或迷你电脑黑屏   | 接上显示器或加装 HDMI 仿真插头                                                                 |
| 屏幕休眠 / 锁定       | 之前正常，闲置后变黑   | 唤醒屏幕；在需要访问的时段保持显示器唤醒；保留密码保护的锁屏                                   |
| 缺少权限（macOS）     | 能连上，但一直黑屏     | 在“隐私与安全性”中授予屏幕录制权限；为登录界面安装辅助程序                                     |
| 编解码器不匹配        | 画面空白或卡住         | 切换编解码器（VP8 / VP9 / AV1 / H.264 / H.265）；回退到软件编解码器                            |
| 硬件加速冲突          | 特定 GPU 上黑屏        | 在会话工具栏或设置中关闭硬件编解码，或切换编解码器                                             |
| GPU 驱动过旧          | 驱动/系统更新后黑屏    | 更新 GPU 驱动（尤其是 NVIDIA）                                                                 |
| Wayland 会话（Linux） | 没有授权提示，画面空白 | 接受 PipeWire/portal 提示，并确认已安装桌面 portal；如果发行版仍提供 X11 会话，也可以改用 X11 |
| 网络 / 中继卡顿       | 卡在“等待画面传输”     | 放行 TCP 21115-21117 和 UDP 21116；WebSocket 客户端还需放行 TCP 21118-21119                    |

### 屏幕休眠、锁定与屏幕保护程序

如果之前正常，机器闲置一段时间后才变黑，那是显示器进入了休眠。

- **Windows：** 设置电源计划，让显示器和整机在你需要远程访问的时段内保持唤醒。RustDesk 以服务方式安装后，可以在锁屏界面连接，因此请保留密码保护的锁屏。
- **macOS：** 在你需要远程访问的时段内阻止显示器休眠——在 **系统设置 → 显示器**（或“锁定屏幕”/节能相关设置）中配置，并让 Mac 接通电源，因为使用电池时的休眠行为不同。
- **Android：** 屏幕必须点亮才能共享，因此连接前请先触摸屏幕将其唤醒。从 iOS 连接屏幕已关闭、处于休眠状态的 Android 设备，是一个[已知的“等待画面传输”案例](https://github.com/rustdesk/rustdesk/issues/11479)——请先唤醒目标设备。

### macOS 权限

macOS 不允许任何应用在未经明确同意的情况下录制屏幕。如果 RustDesk 在 Mac 上能连上却一直黑屏，请打开 **系统设置 → 隐私与安全性 → 屏幕录制**，启用 RustDesk，然后重启应用。如果黑屏只出现在 _登录窗口_，说明 RustDesk 的服务/辅助程序没有安装为在用户登录前运行——请安装它，以支持登录前的屏幕捕获。

### 视频编解码器不匹配

RustDesk 可以用多种方式编码视频流，默认选项并不总适合远程硬件。在会话工具栏（或设置）中切换编解码器——**VP8、VP9、AV1，硬件支持时还有 H.264/H.265**——观察画面是否出现。如果某个硬件编解码器在特定 GPU 上导致画面空白，回退到 VP9 等软件编解码器是稳妥的做法。

### 硬件加速与 GPU 驱动

部分 GPU——最常见的是 NVIDIA 配置——会与 RustDesk 的硬件加速捕获和渲染路径冲突。有两个办法：

- **关闭硬件编解码。** 在会话工具栏（或设置）中关闭 **启用硬件编解码**，让编码回退到软件路径——这能解决许多问题 GPU 上的黑屏。
- **更新 GPU 驱动。** 如果黑屏是在驱动或系统更新后开始出现的，换用最新驱动往往就能解决，NVIDIA 硬件尤其如此。

### Linux 与 Wayland

在 Linux 上，标准 RustDesk 构建版本在已登录的会话中通过 **PipeWire 和 `xdg-desktop-portal`** 捕获 Wayland 桌面，自 1.4.3 起还支持多显示器。portal 会让你选择要共享的显示器，portal v4 及更新版本可以记住这个选择。如果在 Wayland 上画面空白，请接受 portal 的屏幕共享提示，并确认 `xdg-desktop-portal` 和 PipeWire 已安装且正在运行。如果发行版仍提供 X11/Xorg 会话，登录 X11 会话也可以绕开 portal 路径。标准构建版本捕获的是已登录的会话，因此在登录欢迎界面黑屏属于预期行为；另有面向 **x86_64 Debian/Ubuntu 系系统**的 [Wayland 无人值守预览版](/zh-cn/blog/unattended-remote-access-wayland-zh-cn)，增加了无人值守访问和重启后的登录界面访问。

### 网络与中继

提示里有“已连接”字样，说明会话通常已经建立——但如果中继过载或中继端口被阻断，_视频_ 仍可能卡住。对于标准服务器路径，请确保 **TCP 21115-21117 和 UDP 21116** 端到端可达。**只有在使用 WebSocket 客户端时，才需要开放 TCP 21118-21119**。公共演示服务器是共享的，吞吐量没有保证；如果你每天都依赖 RustDesk，自托管中继可以让你自己掌控容量和监控。如果是会话本身频繁断开或始终无法建立，那是另一个问题——请参阅 [RustDesk Server Pro 常见问题](https://rustdesk.com/docs/zh-cn/self-host/rustdesk-server-pro/faq/)。

## 保持所有组件为最新版本

旧版本带着旧的捕获缺陷。请把控制端和被控端**两边**的客户端都更新到最新版本；如果是自托管，也请一并更新服务器。不少黑屏报告在两端都更新之后就自然消失了。

## 开源的优势

当黑屏问题超出这份排查清单时，RustDesk 能提供闭源工具给不了的东西：以 AGPL 协议公开的真实捕获代码。你（或你委托的技术人员）可以准确看懂捕获在你所用平台上的实现方式，复现问题，并向公开仓库提交精确的报告——而不必在厂商的支持队列里苦等。

## 服务器归你所有，变数更少

运行[你自己的中继和 ID 服务器](/zh-cn/blog/why-self-host-remote-desktop-software-zh-cn)，共享的公共基础设施就不再是变量——排查捕获问题时少了一个未知因素，可调节的部分也完全由你掌控。这是在掌控数据之外的一项附带好处。
