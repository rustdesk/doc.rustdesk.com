2026 年 7 月 7 日，RustDesk 内部遥测数据在一台配备 **12 核 CPU 和 32 GB 内存**的公共服务器主机上，记录到**超过 200 万个在线终端**。

有两点界定了这一数字的范围。其一，“在线终端”指的是在该时间点报告为在线的设备，而不是 200 万个同时进行的远程控制会话。其二，这是一次内部生产环境观测，而不是经独立审计的基准测试，也不代表 Server Pro 的容量保证：Server Pro 部署还会增加数据库写入、审计活动、控制台使用、策略处理和中继流量。

## 简短回答

**对 Server Pro 而言，20 万台在线设备是一个切实可行的规划目标。** 上述公共服务器观测在单台 12 核、32 GB 主机上高出一个数量级。试点中需要验证的是 Server Pro 在终端在线之外增加的负载：设备状态变动、策略、审计写入、控制台使用以及并发的中继会话。

## 详细说明

此类规模问题，是我们从正在迁出 TeamViewer 或 AnyDesk 的 IT 团队那里听到的最常见问题之一，尤其是那些计划部署数万乃至数十万台设备的团队。答案取决于有多少设备保持在线、设备状态变化的频率、同时运行的远程会话数量，以及有多少流量经由中继传输。

对于 Server Pro 部署，需要验证公共服务器数据没有覆盖的部分。随着设备上线和下线，缓存和数据库写入性能会变得十分重要。中继带宽和 CPU 占用取决于并发中继会话的数量、时长、分辨率和编解码器。控制台查询、审计保留、设备组、策略以及集成等因素也会带来额外负载，而这些是仅凭终端在线情况无法衡量的。建议在具有代表性的负载测试中，涵盖预期在线设备数、连接变动情况、并发的直连与中继会话数、数据库保留以及管理活动等指标。

进行可复现的 Server Pro 试点时，记录客户端/服务器版本、硬件、数据库和中继的部署位置。分阶段增加在线设备数与状态变动，同时运行预期的控制台查询、策略更新和审计写入。测量注册/重连成功率、连接建立时间、数据库延迟、CPU/内存、磁盘增长及中继吞吐量。另外纳入峰值并发会话和恢复演练；这些测量结果要与在线终端数量分开记录。

高可用性和负载均衡也应同样对待。中继可以横向扩展：你可以运行多个中继，按区域部署，而且 hbbr 中继无需许可证。Pro 许可证绑定到一台 hbbs 服务器，因此请明确设计 ID 服务器和数据库的故障转移方案，并针对超大规模设备群与 RustDesk 一起评审。

然后再确定许可规模：Server Pro 按登录用户和受管设备授权，标准套餐包含无限并发连接。请前往 [rustdesk.com/pricing](https://rustdesk.com/pricing) 为你的设备群选择合适的套餐。
