조직이 GDPR, 의료 개인정보 보호 규정, 혹은 공공 부문의 "데이터는 반드시 자체 인프라에 보관해야 한다"는 요건의 적용을 받는다면, 어떤 원격 데스크톱 도구를 후보에 올릴 수 있는지는 단 하나의 질문으로 결정됩니다. 바로 **세션 데이터가 실제로 어디로 전달되는가**입니다.

벤더가 호스팅하는 서비스에서는 일반적으로 벤더가 연결 조정을 운영하고 관리·계정 데이터를 저장합니다. 세션 미디어는 엔드포인트 사이를 직접 오가거나 릴레이를 거칠 수 있습니다. 데이터 흐름을 검토할 때는 이 경로들을 구분해야 하며, "클라우드가 중개한다"는 말이 모든 화면 패킷이 클라우드를 거친다는 뜻은 아닙니다.

이 글은 **원격 데스크톱 데이터 주권**을 다룹니다. 그 의미는 무엇인지, 규제 산업과 EU 구매자에게 왜 중요한지, 원격 접속 배포의 어떤 부분을 자체 호스팅으로 통제할 수 있는지 살펴보며, RustDesk를 실제 사례로 들겠습니다.

## 원격 접속에서 "데이터 주권"이 의미하는 것

데이터 주권이란 데이터가 물리적으로 저장되고 처리되는 국가의 법률을 따른다는 원칙입니다. 원격 지원에서 민감한 데이터는 전송하는 파일만이 아닙니다. 세션 자체, 즉 화면에 표시되는 내용, 관리 중인 기기 목록, 연결 메타데이터, 그리고 종종 실시간으로 전달되는 픽셀의 라우팅 경로까지 모두 포함됩니다.

핵심 질문은 다음과 같습니다. **어떤 시스템이 메타데이터를 저장하는가, 어떤 시스템이 트래픽을 중계하는가, 그리고 양쪽 엔드포인트는 어디에 있는가?** 자체 호스팅으로 벤더가 운영하는 랑데부 또는 릴레이 서비스를 경로에서 없앨 수는 있지만, 서로 다른 국가에 있는 엔드포인트 간의 세션이 하나의 관할권 안에 머문다고 보장할 수는 없습니다.

## 핵심 차이: 벤더 클라우드 vs. 여러분의 인프라

여기서 결과를 좌우하는 것은 마케팅 문구가 아니라 아키텍처입니다.

**RustDesk Server Pro는 자체 호스팅 방식입니다.** ID/랑데부 서버, 릴레이 서버, 웹 콘솔, 관리 대상 기기 데이터가 여러분이 선택한 인프라에서 실행됩니다. RustDesk는 먼저 홀 펀칭(hole punching)으로 P2P 직접 연결을 시도하며, 실패하면 세션 트래픽이 여러분이 설정한 릴레이를 거칩니다. 이렇게 하면 랑데부/릴레이 계층과 저장된 기기 데이터를 통제할 수 있지만, 직접 연결 트래픽이 어디를 지나는지는 여전히 엔드포인트와 그 네트워크 경로가 결정합니다.

|                           | 벤더 클라우드 도구 | 자체 호스팅 RustDesk                                                         |
| ------------------------- | ------------------ | ---------------------------------------------------------------------------- |
| 세션이 조정되는 곳        | 벤더의 클라우드    | 여러분의 ID/랑데부 서버                                                      |
| 세션 트래픽이 흐르는 경로 | 벤더가 정한 라우팅 | 가능하면 엔드포인트 간 직접 연결, 그렇지 않으면 여러분의 릴레이를 경유       |
| 데이터 레지던시 통제 주체 | 벤더               | 서버 측 위치와 릴레이 정책을 직접 선택(엔드포인트 위치도 여전히 중요)        |
| 클라이언트의 감사 가능성  | 대개 클로즈드소스  | [오픈소스(AGPL)](https://github.com/rustdesk/rustdesk) — 직접 읽고 빌드 가능 |
| 서버 운영 주체            | 벤더               | 여러분의 팀                                                                  |

자체 호스팅을 검토하는 팀들은 랑데부, 릴레이, 관리 시스템의 위치와 운영 주체를 직접 고를 수 있다는 점을 가장 먼저 꼽는 경우가 많습니다.

## 이점 1: 서버 측 데이터 위치를 직접 통제할 수 있습니다

ID, 릴레이, 관리 서비스를 독일 데이터 센터에 두면 해당 서비스와 저장 데이터가 정확히 어디에 있는지 문서화할 수 있습니다. 양쪽 엔드포인트를 요구되는 경계 안에 두고 트래픽이 승인된 릴레이를 거치도록 강제하면 세션 경로까지 제한할 수 있습니다.

## 이점 2: 오픈소스이므로 클라이언트를 직접 검증할 수 있습니다

RustDesk의 **클라이언트와 RustDesk Server OSS(무료 커뮤니티 서버)는 [AGPL 라이선스](https://github.com/rustdesk/rustdesk)를 따르며**, **Server Pro는 상용 독점 자체 호스팅 서버 소프트웨어**입니다. 보안 팀은 클라이언트 코드를 읽고, 엔드포인트에서 무엇을 하는지 감사하고, 직접 빌드할 수 있습니다. 원격 접속에서는 이 점이 평소보다 더 중요합니다. 소프트웨어가 기기 전체를 제어할 권한을 받기 때문에, 규제 산업의 구매자들은 벤더의 말을 믿기보다 클라이언트가 무엇을 하는지 직접 검증하려는 경향이 점점 강해지고 있습니다.

## 이점 3: 차별화된 서버 라이선스 모델

RustDesk 표준 요금제는 **로그인 사용자와 관리 대상 기기 단위**로 라이선스가 산정되며 무제한 동시 연결이 포함됩니다. 정해진 수의 동시 연결을 라이선스하는 요금제는 [Customized V2](https://rustdesk.com/pricing#custom2)뿐입니다. 요구 사항이 바뀌면 언제든 [라이선스를 업그레이드](/ko/blog/upgrade-rustdesk-license-mid-subscription-ko)할 수 있습니다.

이 모델은 여러분의 환경 규모에 맞춰 확장됩니다. [대규모 기기 운영 계획 가이드](/ko/blog/rustdesk-scale-50000-200000-devices-ko)는 최대 200,000대 규모의 배포를 다룹니다. Server Pro는 사용자·기기 그룹 단위의 [접근 제어](https://rustdesk.com/docs/ko/self-host/rustdesk-server-pro/permissions/)를 더하며, Basic 요금제부터 LDAP/OIDC SSO와 커스텀 클라이언트 생성도 제공합니다.

## RustDesk가 ISO 27001, SOC 2, HIPAA 요건에 부합하는 방식

기업 구매 담당자와 의료 분야 팀은 거의 예외 없이 원격 접속 도구가 ISO 27001, SOC 2, HIPAA와 어떻게 맞물리는지 묻습니다. 클라우드 제품이라면 벤더가 자사 인프라에 대해 받은 인증과 책임 공유 조건에 의존하게 됩니다. 자체 호스팅한 RustDesk는 그 반대입니다. ID/랑데부 서버, 릴레이, 콘솔이 여러분의 프로그램이 이미 다루는 인프라에서 실행되므로 여러분의 ISO 27001 적용 범위, SOC 2 통제, HIPAA 보호 조치 아래에서 평가하면 되고, 보안 팀은 그 평가의 일부로 클라이언트 소스를 직접 검토할 수 있습니다. 자체 호스팅은 인증이 아니라 배포 통제이며, 이를 적용 범위 안으로 들여오는 것은 평가입니다.

몇 가지 실무적인 참고 사항입니다.

- 자체 호스팅하면 랑데부 서버, 릴레이, 콘솔, 저장된 관리 데이터의 위치와 운영 주체를 직접 고를 수 있습니다. 이 위치와 함께 엔드포인트 라우팅, 백업, 관리자 접근도 문서화하세요.
- 구매 프로세스에서 벤더 측 SOC 2 보고서, 서명된 BAA(Business Associate Agreement), DPA(데이터 처리 계약), 작성된 보안 설문지를 특별히 요구한다면 [sales@rustdesk.com](mailto:sales@rustdesk.com)으로 RustDesk 팀에 문의해 여러분의 상황에서 현재 제공 가능한 사항을 확인하세요.
- 클라이언트가 오픈소스이므로 "이 소프트웨어가 무엇을 하는지 어떻게 아는가?"라는 질문에는 직접 검사로 답할 수 있습니다. 벤더 보증 보고서는 그와는 다른 조달 질문에 답하는 자료입니다.

요컨대 자체 호스팅은 원격 접속을 여러분이 이미 운영 중인 컴플라이언스 프로그램 안으로 편입시킵니다. 규제 대상 팀에게는 들여다볼 수 없는 인프라에 대한 벤더 인증에 기대는 것보다 대개 더 강한 입지입니다.

## 자체 호스팅 GDPR 프로그램을 뒷받침하는 통제 기능

자체 호스팅은 토대이며, RustDesk는 그 위에 자체 호스팅 팀이 GDPR 프로그램에서 실제로 활용하는 구체적인 통제 기능을 제공합니다.

- **서버 데이터는 여러분이 둔 곳에 머물며, 외부로 나가는 워크플로는 몇 가지로 정해져 있습니다.** 자체 호스팅한 ID/랑데부 서버, 릴레이, Pro 관리 서비스는 여러분이 실행하는 곳에서 배포 데이터를 처리합니다. 문서화해야 할 외부 통신 워크플로는 Pro 라이선스 확인(약 하루 한 번 rustdesk.com으로 HTTPS 통신), 커스텀 클라이언트 빌드 서비스, 클라이언트 업데이트, 외부 메일 서버를 설정한 경우의 SMTP, 연결한 외부 ID 공급자입니다. [Server Pro 오프라인 및 에어갭 가이드](/ko/blog/rustdesk-server-pro-offline-air-gapped-ko)를 참고하세요.
- **감사 로그 보존 기간 설정.** [Server Pro 감사 로그](https://rustdesk.com/docs/ko/self-host/rustdesk-server-pro/audit-logs/#로그-표시-범위와-보존)는 연결, 파일 전송, 알람, 콘솔 작업을 기록합니다. **설정 → 기타 → 로그 보존 기간(일)** 항목에서 `0`은 모든 로그를 무기한 보관하고, 양수를 입력하면 그보다 오래된 로그가 삭제되며, 정리는 1시간마다 실행됩니다. 내보낸 파일과 백업의 보존 기간은 따로 정하세요.
- **세분화되고 범위가 정해진 접근 권한.** [접근 제어](https://rustdesk.com/docs/ko/self-host/rustdesk-server-pro/permissions/)는 사용자별 할당, 기기 그룹, 그룹 간 규칙으로 누가 어떤 기기에 접근할 수 있는지 정합니다(사용자 그룹 권한과 기기 그룹 권한은 누적됩니다). 공유 주소록은 항목을 정리할 뿐 접근 경계가 아닙니다. [제어 역할](https://rustdesk.com/docs/ko/self-host/rustdesk-server-pro/control-role/)은 기술자가 세션 안에서 할 수 있는 작업, 즉 키보드/마우스, 클립보드, 파일 전송, 오디오, 카메라, 터미널, 인쇄, 녹화 등을 제한합니다. SSO/LDAP, 피제어 기기 2단계 인증과 함께 최소 권한 원칙과 목적 제한 원칙을 적용합니다.
- **개인정보 보호 모드와 연결별 동의.** 피제어 측은 수신 연결마다 승인을 요구할 수 있으며, 개인정보 보호 모드(Windows와 macOS에서 지원)는 세션 동안 로컬 화면을 검게 가려 화면에 표시된 개인정보가 우연히 노출되는 것을 줄입니다.
- **여러분의 방식대로 삭제.** 데이터가 여러분의 서버에 있으므로 사용자를 비활성화하거나 제거하고, REST API를 포함한 방법으로 기기와 기록을 삭제하며, 삭제 요청과 보존 관련 요청을 직접 처리할 수 있습니다.
- **지역 내 자체 운영 인프라.** ID/랑데부 서버, 릴레이, 콘솔, 저장 데이터는 여러분이 정한 위치에서, 여러분이 통제하는 하드웨어로 실행됩니다.
- **커스텀 클라이언트 빌드는 일시적입니다.** 브랜드 맞춤 클라이언트 생성은 RustDesk 빌드 서비스를 사용하는 유일한 단계이며, 의도적으로 짧게 유지됩니다. 제출한 빌드 구성은 빌드가 끝나면 삭제되고, 생성된 설치 파일은 약 하루 뒤 자동으로 제거되므로 내려받아 여러분이 승인한 저장소에 보관하세요.

이는 GDPR 프로그램이 실제로 활용할 수 있는 수단입니다. 문서화와 운영은 여전히 여러분의 몫이지만, 정보주체의 요청을 처리하려고 벤더의 대응을 기다릴 필요는 없습니다.

## 직접 가리켜 보여 줄 수 있는 주권

랑데부 서버, 릴레이, 콘솔, 저장 데이터를 직접 호스팅하면 컴플라이언스 프로그램은 구체적인 근거, 즉 여러분이 직접 배치하고 운영하고 감사하는 인프라를 갖게 됩니다. 이는 도착점이 아니라 출발점이지만, 다른 모든 것이 그 위에 세워지는 토대입니다.

## GDPR 및 데이터 주권 배포 체크리스트

자체 호스팅은 선택지를 주고, 배포 과정에서는 그 선택지를 실제 통제로 바꿔야 합니다.

- ID 서버, 릴레이, 콘솔, 백업, 로그, 관리자가 각각 어디에 있는지 문서화합니다.
- P2P 직접 연결 경로와 릴레이 경유 경로를 따로 매핑합니다. 독일에 서버가 있다고 해서 독일과 다른 국가 사이의 직접 연결 세션이 독일 안에만 머무는 것은 아닙니다.
- 통제된 위치를 경유하는 라우팅이 P2P 성능보다 중요한 경우를 판단해, 언제 릴레이 사용을 강제할지 정합니다.
- 기기, 계정, 감사, 연결 메타데이터 각각의 목적, 보존 기간, 접근 정책을 기록합니다.
- 최소 권한 원칙에 따른 기기 그룹, 가능한 경우 MFA/SSO, 기술자를 위한 입사·이동·퇴사(joiner-mover-leaver) 프로세스를 적용합니다.
- 웹 콘솔을 HTTPS 뒤에 두고, 관리용 네트워크 접근을 제한하며, 백업 복구를 테스트합니다.
- 사용 사례에 맞춰 처리 활동 기록, 수탁자(프로세서) 검토, 국외 이전 평가, DPIA(개인정보 영향평가) 등 적절한 법적 평가를 완료합니다.

RustDesk는 데이터 주권 아키텍처를 뒷받침할 수 있지만, 그 아키텍처와 법적 근거에 대한 책임은 컨트롤러에게 있습니다.
