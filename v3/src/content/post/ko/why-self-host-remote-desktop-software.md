대부분의 원격 데스크톱 도구는 한 가지 방식으로 판매됩니다. 클라우드 구독 형태로, 공급사 서버가 세션을 조정하고 직접 경로가 실패하면 릴레이까지 담당합니다. 자체 호스팅은 이 역할을 직접 통제하는 인프라로 옮깁니다. 클라이언트는 자체 ID/랑데부 서버를 통해 조정되고, 가능하면 직접 연결하며, 그렇지 않으면 자체 릴레이를 사용합니다. 이 글에서는 RustDesk Server OSS(무료 커뮤니티 서버)와 Server Pro를 구체적인 예로 들어 자체 호스팅을 해야 하는 이유를 설명합니다.

## "원격 데스크톱 자체 호스팅"이 실제로 의미하는 것

클라우드 전용 방식의 편리함에는 대가가 따릅니다. 기기 목록, 연결 메타데이터, 때로는 세션 트래픽까지 제3자를 거치며, 그 회사의 가동 시간, 가격 정책, 보안 수준에 좌우됩니다.

자체 호스팅은 이 구도를 뒤집습니다. RustDesk에서는 사내 팀이 ID/랑데부 서비스와 릴레이 서비스를 운영하며, Server Pro를 쓰면 웹 콘솔과 저장된 기기 데이터도 자체 인프라에 둡니다. 직접 세션은 엔드포인트 사이를 오가고, 릴레이 세션은 자체 릴레이를 사용합니다. RustDesk의 **클라이언트와 Server OSS는 [AGPL 라이선스](https://github.com/rustdesk/rustdesk)** 이며, **Server Pro는 상용 독점 자체 호스팅 서버 소프트웨어**입니다.

자체 호스팅을 한다고 기능을 포기하는 것은 아닙니다. [MSP](/ko/blog/rustdesk-for-msps-ko)와 사내 IT를 위해 Server Pro는 사용자별·기기 그룹별 [접근 제어](https://rustdesk.com/docs/ko/self-host/rustdesk-server-pro/permissions/)를 갖춘 자체 호스팅 웹 콘솔을 제공하며, Basic 플랜부터는 커스텀 클라이언트 생성기와 [LDAP/OIDC SSO](https://rustdesk.com/docs/ko/self-host/rustdesk-server-pro/ldap/)도 제공합니다. 규모를 포기하는 것도 아닙니다. RustDesk 퍼블릭 서버는 2026년 7월 7일 12코어, 32GB 호스트 한 대에서 200만 개가 넘는 온라인 엔드포인트를 기록했으며(내부 원격 측정 데이터), [대규모 기기 환경 계획 가이드](/ko/blog/rustdesk-scale-50000-200000-devices-ko)에서 Server Pro로 검증해야 할 사항을 다룹니다.

## 서버 운영에 실제로 필요한 것

통제권에는 운영 작업이 따릅니다. 처음 한 번의 설정과 그 뒤의 꾸준한 관리입니다. 구체적인 목록은 다음과 같습니다.

- **호스트를 준비합니다.** RustDesk의 하드웨어 요구 사항은 낮으므로, 온프레미스든 저렴한 VPS든 소규모 Linux VM으로 ID/랑데부 서비스와 릴레이 서비스를 운영할 수 있습니다. 기기 수와, 피어 투 피어가 아니라 릴레이로 처리되는 트래픽의 양에 맞춰 규모를 정하세요.
- **사용하는 포트만 엽니다.** 네이티브 RustDesk 클라이언트는 NAT 테스트, 연결 서비스, 등록, 하트비트, 릴레이를 위해 **TCP 21115-21117과 UDP 21116**이 필요합니다. 21114-21119 범위 전체를 노출하지 마세요. TCP 21118-21119는 WebSocket 백엔드이고, TCP 21114는 Pro HTTP API/콘솔 백엔드입니다. HTTPS/WSS 리버스 프록시가 Pro API와 WebSocket 서비스 앞단에 있다면, 그 트래픽에 대해서는 TCP 443만 외부에 공개하고 21114와 21118-21119는 내부용으로 두세요. 네이티브 클라이언트도 접속한다면, 공개된 443 포트가 네이티브 클라이언트용 핵심 포트를 대신하지는 않습니다. [공식 포트 문서](https://rustdesk.com/docs/ko/self-host/)를 참고하세요.
- **TLS를 설정합니다.** 리버스 프록시에서 HTTPS와 WSS를 종료해, 자격 증명, API 호출, 브라우저 클라이언트 트래픽이 평문 HTTP 콘솔/API나 원시 WebSocket 백엔드를 노출하지 않고 공개 TCP 443을 사용하게 하세요.
- **백업합니다.** 서버에는 기기 목록, 사용자 계정, 주소록, 접근 규칙이 저장됩니다. 백업 일정을 잡고, 실제로 복원할 수 있는지 테스트하세요.
- **패치 주기를 유지합니다.** 새 서버 빌드는 계속 나오며, 그 아래의 OS도 직접 관리해야 합니다. 누가 얼마나 자주 업데이트를 적용할지 정하세요.
- **모니터링합니다.** 이제 조정 서비스는 직접 운영하는 것이므로 가동 시간, 디스크, 릴레이 처리량을 지켜보고 알림과 복구도 직접 책임져야 합니다.

이미 Linux 서버를 운영하는 팀이라면 특별할 것이 없는 작업입니다. 업데이트, 백업, 인증서 갱신, 복원 테스트의 담당자와 일정을 정해 두면 서버는 일상적인 인프라로 운영됩니다.

## 자체 호스팅을 평가하는 방법

- **Server OSS로 시작하세요.** 오늘 오후에 바로 배포하고, 코드를 검토하고, 원하는 만큼 계속 쓸 수 있습니다. 라이선스 비용이나 만료가 없으며, 드는 것은 자체 호스팅 비용과 대역폭뿐입니다.
- **Pro 기능이 필요하신가요?** 최신 플랜 요금은 [rustdesk.com/pricing](https://rustdesk.com/pricing)에서 확인할 수 있으며, 현재 어떤 평가 방법이 있는지는 [sales@rustdesk.com](mailto:sales@rustdesk.com)에서 안내해 드립니다.
- **설치보다 먼저 보고 싶으신가요?** [RustDesk YouTube 채널](https://www.youtube.com/@rustdesk)에 전체 데모 영상이 있습니다.

가격 변경, 비공개 코드, 공급사 클라우드 때문에 대안을 찾게 되었다면, 자체 호스팅은 할인이 아니라 구조적인 해결책입니다. 서버를 어디서 실행하고 누가 운영할지 직접 정할 수 있습니다. 이미 인프라를 운영하는 팀에게는 도약이 아니라 다음 단계입니다. Server OSS로 파일럿을 진행하고, 최대 세션 수에 맞춰 릴레이 규모를 정하고, 워크플로가 안정적으로 돌아가면 전체 기기를 옮기세요.
