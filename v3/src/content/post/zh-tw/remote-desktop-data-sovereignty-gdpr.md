如果你的組織受 GDPR、醫療隱私法規，或公部門「資料必須留在自有基礎架構」的規定約束，有一個問題會決定哪些遠端桌面工具能進入候選名單：**工作階段資料實際上流向哪裡？**

在廠商代管的服務中，通常由廠商營運連線協調，並儲存管理與帳號資料。工作階段的畫面資料可能在端點之間直接傳輸，也可能經過中繼。資料流審查必須區分這些路徑；「由雲端協調」並不代表每個畫面封包都會經過雲端。

本文談的是**遠端桌面資料主權**：它代表什麼、為什麼對受監管產業與歐盟買家很重要，以及自架讓你能掌控遠端存取部署中的哪些部分。我們以 RustDesk 作為實例。

## 「資料主權」對遠端存取代表什麼

資料主權是指資料受其實際儲存與處理所在國家法律管轄的原則。就遠端支援而言，敏感資料不只是你傳輸的檔案，而是工作階段本身：畫面上的內容、你管理的裝置清單、連線中繼資料，往往還有即時畫面像素的傳輸路徑。

核心問題是：**哪些系統儲存中繼資料、哪些系統轉送流量，兩端的端點又在哪裡？** 自架可以把廠商營運的連線協調或中繼服務從路徑中移除，但無法保證位於不同國家的端點之間的工作階段會留在單一司法管轄區內。

## 核心差異：廠商雲端 vs. 你自己的基礎架構

這裡決定結果的是架構，而不是行銷。

**RustDesk Server Pro 是自架的。** ID/連線協調伺服器、中繼伺服器、網頁主控台與受管裝置資料，都在你選擇的基礎架構上執行。RustDesk 會先透過打洞（hole punching）嘗試點對點直連；失敗時，工作階段流量改走你設定的中繼伺服器。這讓你掌控連線協調／中繼層與儲存的裝置資料，但直連流量的傳輸路徑仍取決於端點及其網路路由。

|                    | 廠商雲端工具   | 自架 RustDesk                                                            |
| ------------------ | -------------- | ------------------------------------------------------------------------ |
| 工作階段在哪裡協調 | 廠商的雲端     | 你的 ID/連線協調伺服器                                                   |
| 工作階段流量怎麼走 | 由廠商決定路由 | 盡可能在端點之間直連；否則經過你的中繼伺服器                             |
| 誰掌控資料落地     | 廠商           | 你決定伺服器端位置與中繼政策；端點位置依然重要                           |
| 用戶端可否稽核     | 通常不開放原始碼 | [開源（AGPL）](https://github.com/rustdesk/rustdesk)——可自行閱讀與建置 |
| 誰營運伺服器       | 廠商           | 你的團隊                                                                 |

評估自架的團隊最常先提到的就是這項控制權：自行選擇連線協調、中繼與管理系統的所在地與營運者。

## 優勢一：伺服器端資料的位置由你掌控

把 ID、中繼與管理服務放在德國的資料中心，你就能明確記載這些服務及其儲存資料位於何處。再讓兩端都位於規定的邊界內，並強制流量經過核准的中繼伺服器，連工作階段的路由也能一併限制。

## 優勢二：開源讓你能驗證用戶端

RustDesk 的**用戶端與 RustDesk Server OSS（免費社群伺服器）採用 [AGPL 授權](https://github.com/rustdesk/rustdesk)**；**Server Pro 則是商業、專有的自架伺服器軟體**。你的資安團隊可以閱讀用戶端程式碼、稽核它在端點上做了什麼，並自行建置。這對遠端存取格外重要：這套軟體被賦予完全控制一台電腦的權限，而受監管的買家越來越希望親自驗證用戶端的行為，而不是聽信廠商的說法。

## 優勢三：不同的伺服器授權模式

RustDesk 標準方案依**登入使用者加受管裝置**授權，且不限同時連線數；只有 [Customized V2](https://rustdesk.com/pricing#custom2) 授權固定的同時連線數。需求改變時，你可以隨時[升級授權](/zh-tw/blog/upgrade-rustdesk-license-mid-subscription-zh-tw)。

這個模式會隨你的裝置規模擴展：[大型裝置群規劃指南](/zh-tw/blog/rustdesk-scale-50000-200000-devices-zh-tw)涵蓋最多 20 萬台裝置的部署。Server Pro 增加依使用者與裝置群組設定的[存取控制](https://rustdesk.com/docs/zh-tw/self-host/rustdesk-server-pro/permissions/)，並自 Basic 方案起提供 LDAP/OIDC SSO 與自訂用戶端產生功能。

## RustDesk 如何對應 ISO 27001、SOC 2 或 HIPAA 要求

企業採購與醫療團隊幾乎都會問：遠端存取工具如何對應 ISO 27001、SOC 2 或 HIPAA？使用雲端產品時，你依賴的是廠商對其自身基礎架構的認證，以及責任共擔條款。自架 RustDesk 的情況正好相反：ID/連線協調、中繼與主控台在你的合規計畫已涵蓋的基礎架構上執行，所以你是在自己的 ISO 27001 範圍、SOC 2 控制或 HIPAA 保護措施下評估它們，資安團隊也能把檢視用戶端原始碼納入評估。自架是部署上的控制，不是認證；讓它納入合規範圍的是評估本身。

幾點實務說明：

- 自架讓你選擇連線協調、中繼、主控台與儲存的管理資料的所在地與營運者。請連同這些位置，一併記錄端點路由、備份與管理員存取。
- 如果你的採購明確要求廠商端的 SOC 2 報告、簽署的業務夥伴協議（BAA）、DPA 或填妥的資安問卷，請來信 [sales@rustdesk.com](mailto:sales@rustdesk.com) 詢問 RustDesk 團隊，你的情境目前可提供哪些資料。
- 由於用戶端開源，「怎麼知道它在做什麼？」這個問題可以靠檢視原始碼回答；廠商保證報告回答的則是另一個採購問題。

簡單來說，自架讓遠端存取納入你既有的合規計畫；對受監管的團隊而言，這往往比依賴廠商替你無法檢視的基礎架構所取得的認證更有利。

## 支援自架 GDPR 計畫的控制措施

自架是基礎，RustDesk 在此之上提供自架團隊在 GDPR 計畫中實際倚重的具體控制措施：

- **伺服器資料留在你放置的地方，對外流程只有少數幾項。** 自架的 ID/連線協調、中繼與 Pro 管理服務，會在你執行它們的地方處理部署資料。需要記錄的對外流程包括：Pro 授權驗證（約每天一次以 HTTPS 連到 rustdesk.com）、自訂用戶端建置服務、用戶端更新、設定外部郵件伺服器時的 SMTP，以及你串接的任何外部身分識別提供者。請參閱 [Server Pro 離線與實體隔離指南](/zh-tw/blog/rustdesk-server-pro-offline-air-gapped-zh-tw)。
- **可設定的稽核保留期限。** [Server Pro 稽核日誌](https://rustdesk.com/docs/zh-tw/self-host/rustdesk-server-pro/audit-logs/)涵蓋連線、檔案傳輸、警示與主控台操作。在 **設定 > 其他 > 日誌保留（天）** 中，`0` 代表無限期保留所有日誌；正數則會刪除早於該天數的日誌，每小時清理一次。匯出檔與備份的保留期限請另外訂定。
- **細緻、有範圍的存取權限。** [存取控制](https://rustdesk.com/docs/zh-tw/self-host/rustdesk-server-pro/permissions/)透過個別使用者指派、裝置群組與跨群組規則，決定誰能連到哪些裝置（使用者群組與裝置群組的權限會累加）。共用通訊錄只負責整理項目，不是存取邊界。[控制角色](https://rustdesk.com/docs/zh-tw/self-host/rustdesk-server-pro/control-role/)限制技術人員在工作階段內能做什麼：鍵盤／滑鼠、剪貼簿、檔案傳輸、音訊、攝影機、終端機、列印、錄影等。搭配 SSO/LDAP 與受控裝置的雙重驗證，就能落實最小權限與目的限制。
- **隱私模式與逐次連線同意。** 被控端可要求每次連入連線都需經過核准；隱私模式（支援 Windows 與 macOS）會在工作階段期間讓本機螢幕變黑，降低螢幕上個人資料意外外露的風險。
- **依你的方式刪除資料。** 由於資料存放在你的伺服器上，你可以停用或移除使用者、刪除裝置與紀錄（包括透過 REST API），並直接處理刪除與保存期限相關的請求。
- **區域內、自行營運的基礎架構。** ID/連線協調、中繼、主控台與儲存的資料，都在你放置的地方、你掌控的硬體上執行。
- **自訂用戶端建置是暫時性的。** 產生品牌用戶端是唯一會用到 RustDesk 建置服務的步驟，而且刻意設計得很短暫：你提交的建置設定在建置完成後即刪除，產生的安裝檔約一天後自動移除，所以請下載後存放在你自己核准的儲存庫中。

這些都是 GDPR 計畫真正可以運用的槓桿：你仍然要記錄並執行它們，但不必等廠商回應資料主體的請求。

## 指得出來的主權

自行託管連線協調、中繼、主控台與儲存的資料，能給合規計畫一樣具體的東西：由你放置、營運與稽核的基礎架構。這是基礎而不是終點，卻是其他一切的立足點。

## GDPR 與資料主權部署檢核清單

自架給了你選擇；部署則要把這些選擇轉化為控制措施：

- 記錄 ID 伺服器、中繼伺服器、主控台、備份、日誌與管理員所在的位置。
- 將點對點直連路由與經中繼的路由分開繪製。伺服器設在德國，並不會讓德國與其他國家之間的直連工作階段留在德國境內。
- 決定何時必須強制使用中繼，也就是讓流量經過受控位置比點對點效能更重要的時候。
- 記錄裝置、帳號、稽核與連線中繼資料的處理目的、保存期限與存取政策。
- 套用最小權限的裝置群組、在可行之處啟用 MFA/SSO，並為技術人員建立到職、調職、離職（joiner-mover-leaver）流程。
- 讓網頁主控台走 HTTPS、限制管理端的網路存取，並測試備份還原。
- 依你的使用情境完成適當的法律評估，例如處理活動紀錄、處理者審查、跨境傳輸評估與資料保護影響評估（DPIA）。

RustDesk 可以支援資料主權架構，但架構及其法律依據的責任仍在控制者身上。
