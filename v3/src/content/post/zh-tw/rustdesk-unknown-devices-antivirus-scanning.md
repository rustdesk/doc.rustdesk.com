在 RustDesk 主控台中看到不熟悉的裝置，光憑這一點還不足以判斷成因。防毒軟體的沙箱測試是已知的可能原因之一，但相同的現象也可能源自設定外洩、未經授權的註冊、權杖外流，或部署上的疏失。

## 簡短回答

部分防毒軟體（AV）或端點偵測與回應（EDR）產品，會在雲端沙箱中執行不熟悉的執行檔。如果沙箱拿到的用戶端版本包含您的伺服器設定，且能連到 ID 伺服器，就可能出現短暫的註冊。然而，雲端服務商的 IP 位址或不尋常的硬體名稱，**並不能**證明就是這個原因——攻擊者同樣會使用雲端主機。在排除這起事件之前，請先保留並檢視相關證據。

## 詳細說明

### 發生原因

RustDesk 用戶端執行時，只要能連到已設定的 ID/連線協調伺服器，就可能向它註冊。這讓沙箱執行成為合理的可能原因，公開的 [GitHub 討論串](https://github.com/rustdesk/rustdesk-server-pro/discussions/307)也討論過這一點；但這同時代表，任何取得已設定用戶端或有效部署素材的人，都可能產生類似的註冊。

在為這起事件下結論之前，請先檢視伺服器的註冊與連線日誌、該裝置的首次出現時間與來源 IP、部署紀錄，以及自訂用戶端的散布途徑。視情況更換可能外洩的密碼、API／部署權杖，以及伺服器設定或金鑰。同時檢查相同的帳密是否在其他地方重複使用，並確認該不明裝置是否曾嘗試或完成任何工作階段。

### 如何阻止

主控台中有兩項設定可以解決這個問題，選擇哪一項取決於您是否仍在持續導入真正的新裝置。

**選項一——完全停用新裝置註冊。** 如果您的裝置清單基本上已經穩定、不需要經常新增機器，這是最簡單的做法：前往 **設定 → 其他 → 停用新裝置**（Settings → Others → Disable new devices on web console）。之後無論是沙箱還是其他來源，都完全無法註冊新裝置。

**選項二——要求使用部署權杖。** 如果您仍在持續導入新裝置（例如 MSP 為客戶導入裝置，或 IT 團隊為新機器製作映像檔），一律「停用新裝置」反而會妨礙自己的作業。這時請改為啟用 **設定 → 其他 → 新裝置必須部署後註冊**，建立一個 API 權杖（「裝置」權限，設為讀寫），並讓安裝流程在每台裝置上執行文件中說明的[部署指令](https://rustdesk.com/docs/zh-tw/self-host/client-deployment/)：

```
rustdesk --deploy --token <api_token>
```

[部署文件](https://rustdesk.com/docs/zh-tw/self-host/client-deployment/)明確規定了這個註冊途徑。要求權杖可以擋下只拿到已設定用戶端的沙箱，**前提是權杖沒有包含在該用戶端或其安裝材料中**。持有有效權杖的沙箱或攻擊者仍然可以註冊。請保護權杖的散布、只授予必要的最小權限，並在權杖可能外洩時更換。

**另一項相關但範圍較小的控制：** 如果您希望保持開放註冊，只是想在檢視之前，先讓未指派的裝置不出現在一般使用者眼前，也可以使用 **設定 → 其他 → 僅管理員可存取未指派的裝置**（Only admin can access unassigned devices）。這項設定不會阻止註冊，但能確保一般使用者在您有機會檢視之前，看不到也碰不到任何新出現的裝置。

### 如何評估結果

單憑註冊本身，並不能證明攻擊者控制了另一台端點，但在原因釐清之前，仍應視為未經授權的活動。如果某筆註冊存在時間短暫、與已知的資安掃描時間吻合，之後也沒有任何存取，就可能佐證沙箱的假設。但若出現非預期的工作階段、重複註冊、使用有效的帳密，或已設定好的用戶端被散布到非預期的管道，就需要啟動事件應變。

## 誰會遇到這個問題

無論是 IT 管理員還是 MSP，新的伺服器維運人員通常會在建置自架伺服器後幾天內——也就是在收緊註冊控管之前——遇到這個問題。及早調查很重要，因為無害的掃描與未經授權的註冊，在主控台中看起來可能非常相似。
