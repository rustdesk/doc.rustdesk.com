如果 RustDesk 顯示 **「已連線，等待畫面傳輸...」**（英文介面為 "Connected, waiting for image"），接著出現黑畫面，其實最困難的部分已經完成：兩端已經找到彼此，工作階段也已經建立。缺少的是*畫面*。最常見的情況是遠端電腦沒有可以擷取的畫面；比較少見的是編解碼器、GPU 驅動程式或中繼路徑讓串流卡住。本指南從最常被回報的原因一路談到邊緣案例，並為每一種原因提供具體的修正方法。

## 簡短答案

工作階段已經連上，但沒有收到畫面。最常被回報的原因是遠端電腦沒有可以擷取的畫面：**沒有接螢幕、顯示器進入休眠，或缺少螢幕錄製權限**。請給 RustDesk 一個實際存在、處於喚醒狀態的顯示器（螢幕、HDMI 假負載插頭或虛擬顯示器）與正確的權限；如果畫面仍未出現，再改用 VP9 等其他編解碼器。若還是黑畫面，請更新 GPU 驅動程式，並確認中繼連接埠可以連通。

## 從這裡開始：有沒有東西可以擷取？

最常被回報的原因是**無螢幕主機**——沒有接螢幕，或顯示器已經休眠的伺服器、迷你電腦或工作站。沒有作用中的顯示器時，往往就沒有畫面緩衝區（framebuffer）可以擷取，因此 RustDesk 雖然連上了，卻沒有東西可以傳送。這種狀況在 RustDesk 的問題追蹤系統中一再出現，包括[目標端螢幕關閉時才出現黑畫面的回報](https://github.com/rustdesk/rustdesk/issues/9884)，以及長期存在的[「Connected, waiting for image」討論串](https://github.com/rustdesk/rustdesk/issues/222)。

讓它有東西可以擷取的兩種方法：

- **接上螢幕**，並確認螢幕已開啟且處於喚醒狀態。
- **使用 HDMI（或 DisplayPort）假負載插頭。** 這種便宜的轉接頭會讓 GPU 以為接了顯示器，於是持續繪製畫面緩衝區供 RustDesk 擷取。這是無螢幕桌機與家用伺服器的標準解法。

如果*確實*接了螢幕，下一個嫌疑就是它進入了休眠。

| 硬體加速衝突             | 特定 GPU 上出現黑畫面            | 在工作階段工具列或設定中關閉硬體編解碼器，或切換編解碼器                                       |

### 螢幕休眠、鎖定與螢幕保護程式

如果之前正常，電腦閒置一段時間後才變黑畫面，就是顯示器進入了休眠。

- **Windows：** 設定電源計畫，讓顯示器與電腦在需要遠端存取的時段保持喚醒。將 RustDesk 安裝為服務後，在鎖定畫面也能連線，所以請保留密碼保護的鎖定。
- **macOS：** 在需要遠端存取的時段，不要讓顯示器休眠——到**系統設定 → 顯示器**（或「鎖定畫面」／「能源」設定）中調整，並讓 Mac 接上電源，因為使用電池時的休眠行為不同。
- **Android：** 螢幕必須亮著才能分享，連線前請先觸碰螢幕喚醒它。從 iOS 連到螢幕已關閉、處於休眠的 Android 裝置，是[已知的「等待畫面傳輸」情況](https://github.com/rustdesk/rustdesk/issues/11479)——請先喚醒目標裝置。

### macOS 權限

macOS 不允許任何應用程式在未經明確同意下錄製螢幕。如果 RustDesk 在 Mac 上連得上卻一直黑畫面，請開啟**系統設定 → 隱私權與安全性 → 螢幕錄製**，啟用 RustDesk，再重新啟動應用程式。如果黑畫面*只出現在登入視窗*，代表 RustDesk 的服務／輔助程式沒有安裝成可在使用者登入前執行——請安裝它以便在登入前擷取畫面。

### 視訊編解碼器不相容

RustDesk 可以用多種方式編碼串流，而預設值不一定適合遠端硬體。請在工作階段工具列（或設定）中切換編解碼器——**VP8、VP9、AV1，或在硬體支援時使用 H.264/H.265**——並觀察畫面是否出現。如果硬體編解碼器在某張 GPU 上產生空白畫面，改回 VP9 等軟體編解碼器是最可靠的做法。

### 硬體加速與 GPU 驅動程式

有些 GPU——最常見的是 NVIDIA 的配置——會和 RustDesk 的硬體加速擷取與繪製路徑衝突。有兩個方法可以處理：

- **關閉硬體編解碼器。** 在工作階段工具列（或設定）中取消**啟用硬體編解碼器**，讓編碼改走軟體路徑——許多有問題的 GPU 上，這樣就能解決黑畫面。
- **更新 GPU 驅動程式。** 在驅動程式或作業系統更新後才出現的黑畫面，改用最新的驅動程式通常就能解決，NVIDIA 硬體尤其如此。

### Linux 與 Wayland

在 Linux 上，標準 RustDesk 版本會在已登入的工作階段中，透過 **PipeWire 與 `xdg-desktop-portal`** 擷取 Wayland 桌面，自 1.4.3 起也包含多螢幕。portal 會請你選擇要分享的顯示器，portal v4 以上版本可以記住這個選擇。如果在 Wayland 上出現空白畫面，請接受 portal 的螢幕分享提示，並確認 `xdg-desktop-portal` 與 PipeWire 已安裝且正在執行。發行版仍提供 X11/Xorg 工作階段時，改用它登入也能避開 portal 路徑。標準版本擷取的是已登入的工作階段，因此在登入畫面看到黑畫面是預期中的行為；另外推出、適用於 **x86_64 Debian/Ubuntu 系統**的 [Wayland 無人值守預覽版](/zh-tw/blog/unattended-remote-access-wayland-zh-tw)，則加入了無人值守存取，以及重新開機後的登入畫面存取。

### 網路與中繼

由於訊息中有「已連線」，工作階段通常已經建立——但如果中繼伺服器過載或中繼連接埠被封鎖，*視訊*仍然可能卡住。標準伺服器路徑請確認 **TCP 21115-21117 與 UDP 21116** 從頭到尾都能連通。**只有使用 WebSocket 用戶端時，才開放 TCP 21118-21119**。公共示範伺服器是共用的，傳輸量沒有保證，因此如果你每天都要用 RustDesk，自架中繼伺服器就能掌控容量與監控。如果是工作階段本身一直斷線或根本建立不起來，那是另一個問題——請參閱 [RustDesk Server Pro 常見問題](https://rustdesk.com/docs/zh-tw/self-host/rustdesk-server-pro/faq/)。

## 隨時保持最新版本

舊版本帶著舊的擷取錯誤。請把控制端與受控端的用戶端**都**更新到最新版本；如果有自架伺服器，也請一併更新。不少黑畫面回報，只要兩端都更新後就消失了。

## 開放原始碼的優勢

當黑畫面怎麼照清單排查都解決不了時，RustDesk 提供了閉源工具沒有的東西：以 AGPL 授權公開的實際擷取程式碼。你（或委託的工程師）可以直接閱讀擷取功能在你的平台上如何運作、重現問題，並向公開儲存庫提交精確的問題回報——不必在廠商的客服佇列裡苦等。

## 伺服器是自己的，變數就更少

架設[自己的中繼與 ID 伺服器](/zh-tw/blog/why-self-host-remote-desktop-software-zh-tw)，共用的公共基礎設施就不再是變數——追查擷取問題時少一個未知因素，可以調整的部分也完全由你掌控。這是在掌握資料之外，一項不太顯眼的額外好處。
