多くのリモートデスクトップツールは、一つの形でしか売られていません。クラウドのサブスクリプションで、ベンダーのサーバーがセッションを調整し、直接の経路がとれないときはリレーで中継する、という形です。セルフホストすると、これらの役割を自社で管理するインフラに移せます。クライアントは自社のID/ランデブーサーバーを通じて接続を調整し、可能なら直接つながり、無理なら自社のリレーにフォールバックします。本記事では、RustDesk Server OSS（無料のコミュニティサーバー）とServer Proを具体例に、その利点を説明します。

## 「リモートデスクトップをセルフホストする」とは実際どういうことか

クラウド専用の手軽さと引き換えに、デバイスの一覧、接続のメタデータ、ときにはセッションの通信までもが第三者を経由します。稼働率も、料金も、セキュリティ体制も、その第三者次第です。

セルフホストはこの構図を逆にします。RustDeskでは、ID/ランデブーサービスとリレーサービスを自社のチームが運用し、Server ProではWebコンソールと保存されるデバイスのデータも自社のインフラに置かれます。直接セッションはエンドポイント間を流れ、リレー経由のセッションは自社のリレーを使います。RustDeskの<strong>クライアントとServer OSSは[AGPLライセンス](https://github.com/rustdesk/rustdesk)</strong>で、**Server Proは商用のプロプライエタリなセルフホスト型サーバーソフトウェア**です。

## クラウド専用型とセルフホスト型をひと目で比較

|                                    | 一般的なクラウド専用ツール                               | セルフホスト型（RustDesk Server Pro）                                                                                                         |
| ---------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| セッションを仲介する場所           | ベンダーのクラウド                                       | 自社のオンプレミスのマシンまたはVPS                                                                                                           |
| データの所在地                     | ベンダーが管理                                           | サーバー側のサービスは自社が管理するインフラで稼働。ただし[エンドポイント間の経路も重要](/ja/blog/remote-desktop-data-sovereignty-gdpr-ja) |
| ライセンスされる同時接続／チャネル | プランごとの枠                                           | 標準プランは無制限、Customized V2はライセンスされた同時接続枠                                                                                 |
| 料金モデル                         | 製品ごとのユーザー数、エンドポイント数、接続数の枠       | [ログインユーザー数＋管理対象デバイス数](https://rustdesk.com/pricing)。Customized V2は同時接続数もライセンス                                 |
| ソースコード                       | 製品によるが、プロプライエタリが一般的                   | 監査できるAGPLのクライアント                                                                                                                  |
| 障害時の依存先                     | ベンダーの稼働率                                         | 自社の運用                                                                                                                                    |
| サーバーの運用者                   | ベンダー                                                 | 自社                                                                                                                                          |

セルフホストしても機能が犠牲になるわけではありません。[MSP](/ja/blog/rustdesk-for-msps-ja)や社内IT向けに、Server Proはユーザー単位・デバイスグループ単位の[アクセス制御](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/permissions/)を備えたセルフホスト型のWebコンソールを提供し、Basicプランからはカスタムクライアントジェネレーターと[LDAP/OIDC SSO](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/ldap/)も使えます。スケールも犠牲になりません。2026年7月7日、RustDeskのパブリックサーバーは12コア・32GBのホスト1台で200万を超えるオンラインのエンドポイントを記録しました（社内テレメトリ）。Server Proで検証すべき点は、[大規模フリートの計画ガイド](/ja/blog/rustdesk-scale-50000-200000-devices-ja)で解説しています。

## サーバーの運用に実際に必要なこと

管理権限には運用の作業が伴います。最初のセットアップと、その後の日常的な保守です。具体的には次のとおりです。

- **ホストを用意する。** RustDeskのハードウェア要件は低いため、オンプレミスでも安価なVPSでも、控えめなLinux VMでID/ランデブーとリレーのサービスを動かせます。デバイスの台数と、ピアツーピアではなくリレー経由になる通信量に合わせてサイズを決めてください。
- **使うポートだけを開ける。** ネイティブのRustDeskクライアントは、NATテスト、接続サービス、登録、ハートビート、リレーのために**TCP 21115〜21117とUDP 21116**を必要とします。21114〜21119の範囲をすべて公開しないでください。TCP 21118〜21119はWebSocketのバックエンド、TCP 21114はProのHTTP API／コンソールのバックエンドです。HTTPS/WSSのリバースプロキシをProのAPIとWebSocketサービスの前に置く場合は、その通信用に公開するのはTCP 443だけにし、21114と21118〜21119は内部にとどめます。ネイティブクライアントも接続する場合、公開した443はネイティブクライアント用のコアポートの代わりにはなりません。[公式のポートリファレンス](https://rustdesk.com/docs/ja/self-host/)を参照してください。
- **TLSを設定する。** HTTPSとWSSをリバースプロキシで終端し、認証情報、API呼び出し、ブラウザクライアントの通信が、平文HTTPのコンソール／APIや生のWebSocketバックエンドを公開せずに、公開したTCP 443を使うようにします。
- **バックアップを取る。** サーバーにはデバイスの一覧、ユーザーアカウント、アドレス帳、アクセスルールが保存されています。バックアップをスケジュールし、実際に復元できることを確かめてください。
- **パッチ適用のペースを決める。** サーバーの新しいビルドは随時リリースされ、その下のOSも自社の管理です。誰がどのくらいの頻度で更新を適用するかを決めておきます。
- **監視する。** 接続を調整するサービスは自社のものになるので、稼働率、ディスク、リレーのスループットを監視し、アラートと復旧も自社で受け持ちます。

すでにLinuxサーバーを運用しているチームにとって、どれも特別なことではありません。更新、バックアップ、証明書の更新、復元テストの担当者とスケジュールを決めれば、サーバーはいつものインフラとして動きます。

## セルフホストの検討の進め方

- **まずはServer OSSから。** 今日の午後にでも導入でき、コードを確認して、好きなだけ運用できます。ライセンス料も有効期限もなく、かかるのは自社のホスティングと帯域の費用だけです。
- **Proの機能が必要なら。** 最新のプラン料金は[rustdesk.com/pricing](https://rustdesk.com/pricing)に掲載しており、現在利用できる評価の選択肢は[sales@rustdesk.com](mailto:sales@rustdesk.com)でご案内しています。
- **インストールより先に見てみたいなら。** [RustDeskのYouTubeチャンネル](https://www.youtube.com/@rustdesk)に、詳しいデモ動画があります。

値上げ、非公開のコード、ベンダーのクラウドがきっかけで乗り換えを考え始めたのなら、セルフホストは値引きではなく構造的な解決策です。サーバーをどこで動かし、誰が運用するかを自社で選べます。すでにインフラを運用しているチームにとっては飛躍ではなく次の一歩です。Server OSSで試験導入し、ピーク時のセッションに合わせてリレーのサイズを決め、ワークフローが問題なく回ることを確かめてからフリートを移行してください。
