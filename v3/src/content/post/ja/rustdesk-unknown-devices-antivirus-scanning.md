RustDeskコンソールに見覚えのないデバイスが表示されたというだけでは、その原因はわかりません。アンチウイルスのサンドボックス実行はよく知られた可能性のひとつですが、同じ症状は、設定情報の漏えい、不正な登録、トークンの流出、展開作業のミスでも起こります。

## 結論から言うと

一部のアンチウイルス／EDR製品は、見慣れない実行ファイルをクラウド上のサンドボックスで実行します。サーバー設定を含むクライアントビルドがサンドボックスに渡り、IDサーバーに到達できれば、短時間だけ登録されることがあります。ただし、クラウド事業者のIPアドレスや見慣れないハードウェア名は、この説明の証拠には**なりません**。攻撃者もクラウドのホストを使うからです。片付けてしまう前に、証拠を保全して確認してください。

## 詳細

### なぜこれが起きるのか

RustDeskクライアントは、実行されて設定済みのID/ランデブーサーバーに到達できると、そのサーバーに登録されることがあります。そのためサンドボックスでの実行は十分に考えられる原因で、公開されている[GitHubのスレッド](https://github.com/rustdesk/rustdesk-server-pro/discussions/307)でも議論されています。しかし同時に、設定済みのクライアントや有効な展開用の資材を手に入れた人なら誰でも、同じような登録を起こせるということでもあります。

この事象を判断する前に、サーバーの登録ログと接続ログ、デバイスが最初に確認された時刻と送信元IP、展開記録、カスタムクライアントの配布経路を確認してください。流出した可能性のあるパスワード、API／デプロイトークン、サーバー設定や鍵は、必要に応じてローテーションします。同じ認証情報がほかの場所で使い回されていないか、そしてその見覚えのないデバイスがセッションを試みたか、実際に確立したかも確認してください。

### 防止する方法

コンソールの2つの設定で対処できます。どちらが合うかは、実際の新しいデバイスを今も積極的に追加しているかどうかで決まります。

**選択肢1 — 新しいデバイスの登録を完全に無効にする。** デバイスの一覧がほぼ固まっていて、マシンを定期的に追加していないなら、これが最もシンプルな方法です。**設定 → その他**で、新しいデバイスを無効にする設定（Disable new devices on web console）をオンにしてください。サンドボックスであるかどうかにかかわらず、新しいデバイスは一切登録できなくなります。

**選択肢2 — デプロイトークンを必須にする。** 今も定期的に新しいデバイスを展開している場合（顧客を追加するMSPや、新しいマシンにイメージを展開するIT部門など）、「新しいデバイスを無効にする」という一律の設定はかえって業務の妨げになります。代わりに **設定 → その他 → 新しいデバイスにデプロイを必須にする** を有効にし、APIトークン（Devices権限、Read and write）を作成したうえで、インストール手順の中で各デバイスに対してドキュメントに記載された[デプロイコマンド](https://rustdesk.com/docs/ja/self-host/client-deployment/)を実行してください。

```
rustdesk --deploy --token <api_token>
```

[デプロイのドキュメント](https://rustdesk.com/docs/ja/self-host/client-deployment/)に、この登録手順が定められています。トークンを必須にすれば、設定済みのクライアントだけを受け取ったサンドボックスの登録を防げます。ただし、**トークンがそのクライアントやインストール資材に含まれていない場合に限ります**。有効なトークンを持つサンドボックスや攻撃者は、それでも登録できます。トークンの配布経路を守り、必要最小限の権限にし、流出した可能性があればトークンをローテーションしてください。

**関連する、より限定的な設定：** 登録自体は開放したままで、確認が済むまで未割り当てのデバイスを表示させたくない場合は、**設定 → その他**に、未割り当てのデバイスに管理者だけがアクセスできるようにする設定（Only admin can access unassigned devices）もあります。登録そのものは止まりませんが、確認する前に現れたデバイスを一般ユーザーが見たり操作したりすることはできなくなります。

### 結果を評価する方法

登録されたという事実だけでは、攻撃者が別のエンドポイントを操作していた証明にはなりませんが、説明がつくまでは不正な行為として扱うべきです。既知のセキュリティスキャンの時期と一致し、その後のアクセスがない短時間の登録であれば、サンドボックスが原因だという仮説を裏付ける材料になります。想定外のセッション、繰り返される登録、有効な認証情報の使用、本来の配布経路以外での設定済みクライアントの配布があれば、インシデント対応が必要です。

## よくこの質問をする人

IT管理者でもMSPでも、新たにサーバーを運用し始めた担当者は、セルフホストのサーバーを立ち上げて数日以内、登録の管理をまだ厳しくしていない段階でこの状況に出くわしがちです。無害なスキャンと不正な登録はコンソール上では似て見えることがあるため、早めに調査することが重要です。
