RustDeskで<strong>「Connected, waiting for image」</strong>（日本語版の表示は「接続完了、映像を待機しています...」）と出たまま黒い画面になる場合、難しい部分はすでにうまくいっています。両端が互いを見つけ、セッションは確立されています。足りないのは*映像*だけです。多くの場合、リモートのマシンにキャプチャする対象がなく、まれにコーデック、GPUドライバー、リレーの経路が原因でストリームが止まります。このガイドでは、最もよく報告される原因から特殊なケースまで、それぞれの原因と具体的な対処法を順に説明します。

## 結論から言うと

セッションは接続されていますが、映像が届いていません。最もよく報告される原因は、リモートのマシンにキャプチャする対象がないことです。つまり、**モニターが接続されていない、ディスプレイがスリープしている、画面収録の権限がない**のいずれかです。RustDeskに実在し、起きているディスプレイ（モニター、HDMIダミープラグ、仮想ディスプレイ）と適切な権限を与え、それでも映像が出なければVP9など別のコーデックに切り替えてください。まだ黒いままなら、GPUドライバーを更新し、リレーのポートに到達できるかを確認します。

## まず確認：キャプチャする対象はあるか？

最もよく報告される原因は**ヘッドレスのマシン**です。モニターを接続せずに稼働しているサーバー、ミニPC、ワークステーションや、ディスプレイがスリープしたままのマシンが該当します。アクティブなディスプレイがないと、キャプチャできるフレームバッファがないことが多く、RustDeskは接続できても送るものがありません。このパターンはRustDeskのIssueトラッカーで繰り返し報告されており、[対象機のモニターがオフのときに限って黒い画面になるという報告](https://github.com/rustdesk/rustdesk/issues/9884)や、長く続いている[「Connected, waiting for image」のスレッド](https://github.com/rustdesk/rustdesk/issues/222)があります。

キャプチャする対象を用意する方法は2つあります。

- **モニターを接続する。** 電源が入っていて、スリープしていないことを確認してください。
- **HDMI（またはDisplayPort）のダミープラグを使う。** この安価なアダプターはGPUにディスプレイが接続されていると認識させるため、GPUはRustDeskが取り込むフレームバッファを描画し続けます。ヘッドレスのデスクトップやホームサーバーでは定番の対処法です。

モニターが*接続されている*なら、次に疑うのはスリープです。

## 原因別の対処法

| 原因                                 | 兆候                                         | 対処法                                                                                                                       |
| ------------------------------------ | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| ヘッドレス／ディスプレイなし         | サーバーやミニPCで黒い画面になる             | モニターを接続するか、HDMIダミープラグを追加する                                                                             |
| 画面のスリープ／ロック               | 以前は映っていたが、放置後に黒い画面になる   | 画面を起こす。アクセスする時間帯はディスプレイをスリープさせない。パスワード付きのロックは有効のままにする                   |
| 権限不足（macOS）                    | 接続はするが、ずっと黒い画面のまま           | 「プライバシーとセキュリティ」で画面収録を許可する。ログイン画面用にヘルパーをインストールする                               |
| コーデックの不一致                   | 画面が空白になる、または固まる               | コーデックを切り替える（VP8／VP9／AV1／H.264／H.265）。ソフトウェアコーデックに戻す                                          |
| ハードウェアアクセラレーションの競合 | 特定のGPUで黒い画面になる                    | セッションのツールバーか設定でハードウェアコーデックをオフにする、またはコーデックを切り替える                               |
| GPUドライバーが古い                  | ドライバーやOSの更新後に黒い画面になる       | GPUドライバーを更新する（特にNVIDIA）                                                                                        |
| Waylandセッション（Linux）           | 同意のプロンプトが出ず、画面が空白           | PipeWire／ポータルのプロンプトを承認し、デスクトップポータルが入っていることを確認する。X11セッションを選べる環境ではそれも可 |
| ネットワーク／リレーの停滞           | 「waiting for image」のまま進まない          | TCP 21115〜21117とUDP 21116を許可する。WebSocketクライアントにはTCP 21118〜21119を追加する                                   |

### 画面のスリープ、ロック、スクリーンセーバー

以前は映っていたのに、マシンをしばらく放置した後で黒くなったなら、ディスプレイがスリープしています。

- **Windows：** リモートアクセスが必要な時間帯は、ディスプレイとマシンがスリープしないよう電源プランを設定してください。RustDeskをサービスとしてインストールしていればロック画面でも接続できるので、パスワード付きのロックは有効のままにしておきます。
- **macOS：** リモートアクセスが必要な時間帯は、ディスプレイがスリープしないようにします。**システム設定 → ディスプレイ**（またはロック画面／省エネルギーの設定）で設定し、バッテリー駆動ではスリープの挙動が変わるため、Macは電源アダプターにつないでおいてください。
- **Android：** 画面がオンでないと共有できないため、接続前に画面に触れて起こしてください。画面がオフで休止中のAndroid端末にiOSから接続するのは、[「waiting for image」の既知のケース](https://github.com/rustdesk/rustdesk/issues/11479)です。先に対象の端末を起こしてください。

### macOSの権限

macOSは、明示的な同意がない限り、どのアプリにも画面の収録を許可しません。MacでRustDeskが接続はするものの黒い画面のままなら、**システム設定 → プライバシーとセキュリティ → 画面収録**を開いてRustDeskを有効にし、アプリを再起動してください。*ログインウィンドウでだけ*黒い画面になる場合は、ユーザーがログインする前に動くRustDeskのサービス／ヘルパーがインストールされていません。ログイン前の画面をキャプチャするには、これをインストールしてください。

### 映像コーデックの不一致

RustDeskはストリームを複数の方式でエンコードでき、既定の方式がリモート側のハードウェアに合うとは限りません。セッションのツールバー（または設定）でコーデックを**VP8、VP9、AV1、またはハードウェアが対応していればH.264/H.265**に切り替え、映像が出るかを確かめてください。特定のGPUでハードウェアコーデックの映像が空白になる場合は、VP9などのソフトウェアコーデックに戻すのが確実です。

### ハードウェアアクセラレーションとGPUドライバー

一部のGPU（最も多いのはNVIDIAの構成）は、RustDeskのハードウェアアクセラレーションを使ったキャプチャや描画の処理と競合します。効果のある対処は2つです。

- **ハードウェアコーデックをオフにする。** セッションのツールバー（または設定）で**ハードウェアコーデックを有効化する**（Use hardware codec）をオフにし、エンコードをソフトウェア処理に切り替えます。問題のある多くのGPUで、これで黒い画面が解消します。
- **GPUドライバーを更新する。** ドライバーやOSの更新後に始まった黒い画面は、最新のドライバーにすると直ることがよくあります。特にNVIDIAのハードウェアで顕著です。

### LinuxとWayland

Linuxでは、標準のRustDeskビルドが、ログイン中のセッションで<strong>PipeWireと`xdg-desktop-portal`</strong>を通じてWaylandのデスクトップをキャプチャします。1.4.3以降は複数のモニターにも対応しています。ポータルは共有するディスプレイを選ぶよう求め、ポータルのバージョン4以降ではその選択を記憶できます。Waylandで画面が空白になる場合は、ポータルの画面共有のプロンプトを承認し、`xdg-desktop-portal`とPipeWireがインストールされて動作していることを確認してください。ディストリビューションがX11/Xorgのセッションを提供している場合は、そちらにログインすればポータルを経由せずに済みます。ログイン画面（グリーター）で黒い画面になるのは、ログイン中のセッションをキャプチャする標準ビルドでは想定どおりの動作です。別途提供している**x86_64のDebian/Ubuntu系システム**向けの[Wayland無人アクセスのプレビュー版](/ja/blog/unattended-remote-access-wayland-ja)では、無人アクセスと再起動後のログイン画面へのアクセスが加わります。

### ネットワークとリレー

メッセージに「connected」とある以上、セッション自体はたいてい確立しています。ただし、リレーが過負荷だったり、リレーのポートがブロックされていたりすると、*映像*だけが止まることがあります。標準のサーバー構成では、**TCP 21115〜21117とUDP 21116**に両端から到達できることを確認してください。**TCP 21118〜21119はWebSocketクライアントを使う場合だけ**開放します。パブリックのデモサーバーは共有で、スループットは保証されていません。RustDeskを毎日使うなら、リレーをセルフホストすれば容量と監視を自分で管理できます。セッション自体が切れる、またはそもそも確立しない場合は別の問題です。[RustDesk Server ProのFAQ](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/faq/)を参照してください。

## すべてを最新の状態に保つ

古いビルドには、古いキャプチャのバグが残っています。操作する側と操作される側の**両方**のクライアントを最新のリリースに更新し、セルフホストしている場合はサーバーも更新してください。両端を更新しただけで消える黒い画面の報告もいくつもあります。

## オープンソースならではの強み

チェックリストを試しても黒い画面が直らないとき、RustDeskにはクローズドソースのツールにないものがあります。AGPLライセンスで公開されている、実際のキャプチャのコードです。自分で（あるいは委託先のエンジニアが）、使っているプラットフォームでキャプチャがどう動くかをコードで確認し、問題を再現して、ベンダーのサポート待ちをせずに公開リポジトリへ的確な報告を出せます。

## サーバーが自分のものなら、変数が減る

[自社でリレーとIDサーバーを運用](/ja/blog/why-self-host-remote-desktop-software-ja)すれば、共有のパブリックインフラが要素から外れます。キャプチャの問題を追うときに不確定要素が一つ減り、調整できる部分はすべて自分で管理できます。データを自社に置けることに加えた、地味ながら確かなメリットです。
