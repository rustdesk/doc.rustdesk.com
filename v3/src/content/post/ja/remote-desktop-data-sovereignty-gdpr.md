自社がGDPR、医療分野のプライバシー規制、あるいは「データは自社インフラ内にとどめる」という公共部門の要件に縛られている場合、どのリモートデスクトップツールを候補に入れられるかは、ひとつの問いで決まります。**セッションデータは実際にはどこを通るのか？**

ベンダーがホストするサービスでは、一般に接続の調整はベンダーが運用し、管理データやアカウントデータもベンダーが保存します。セッションの映像や操作はエンドポイント間を直接流れることもあれば、リレーを経由することもあります。データフローの審査ではこれらの経路を区別する必要があります。「クラウドが仲介する」からといって、画面のパケットがすべてクラウドを通るわけではありません。

本ガイドのテーマは**リモートデスクトップのデータ主権**です。それが何を意味するのか、規制対象の組織やEUの購入者にとってなぜ重要なのか、そしてリモートアクセス環境のどの部分をセルフホスティングで管理できるのかを、RustDeskを例に解説します。

## リモートアクセスにおける「データ主権」の意味

データ主権とは、データが物理的に保存・処理されている国の法律に従うという原則です。リモートサポートで機密性が高いのは、転送するファイルだけではありません。セッションそのもの、つまり画面に表示される内容、管理しているデバイスの一覧、接続に関するメタデータ、そして多くの場合リアルタイムで流れる画面データの経路も含まれます。

核心となる問いは次のとおりです。**どのシステムがメタデータを保存し、どのシステムがトラフィックを中継し、両方のエンドポイントはどこにあるのか？** セルフホスティングでベンダーが運用するランデブーサービスやリレーサービスを経路から外すことはできますが、異なる国にあるエンドポイント間のセッションが1つの法域内にとどまることまでは保証できません。

## 本質的な違い：ベンダーのクラウド vs. 自社インフラ

ここで結果を左右するのは、マーケティングではなくアーキテクチャです。

**RustDesk Server Proはセルフホスト型です。** ID/ランデブーサーバー、リレーサーバー、Webコンソール、管理対象デバイスのデータは、自分で選んだインフラ上で動きます。RustDeskはまずホールパンチングによる直接のピアツーピア接続を試み、それが失敗した場合はセッションのトラフィックが設定済みのリレーを経由します。これによりランデブー／リレー層と保存されるデバイスデータを管理できますが、直接接続のトラフィックがどこを通るかは、引き続きエンドポイントとそのネットワーク経路で決まります。

| | ベンダークラウド型ツール | セルフホスト型RustDesk |
| --- | --- | --- |
| セッションの調整場所 | ベンダーのクラウド | 自社のID/ランデブーサーバー |
| セッショントラフィックの経路 | ベンダーが定める経路 | 可能な場合はエンドポイント間で直接、それ以外は自社のリレー経由 |
| データレジデンシーの管理主体 | ベンダー | サーバー側の設置場所とリレーポリシーは自社で選択（エンドポイントの所在地も影響する） |
| クライアントの監査可能性 | 通常はクローズドソース | [オープンソース（AGPL）](https://github.com/rustdesk/rustdesk) — 自分でコードを読み、ビルドできる |
| サーバーの運用者 | ベンダー | 自社チーム |

セルフホスティングを検討するチームがまず挙げることが多いのが、このコントロール、つまりランデブーサーバー、リレー、管理システムの設置場所と運用者を自分で選べることです。

## メリット1：サーバー側のデータの設置場所を管理できる

ID、リレー、管理サービスをドイツのデータセンターに配置すれば、それらのサービスと保存データがどこにあるかを正確に文書化できます。さらに両方のエンドポイントを必要な境界内に置き、トラフィックをその承認済みリレー経由に強制すれば、セッションの経路も制限できます。

## メリット2：オープンソースだからクライアントを検証できる

RustDeskの<strong>クライアントとRustDesk Server OSS（無料のコミュニティサーバー）は[AGPLライセンス](https://github.com/rustdesk/rustdesk)</strong>で、**Server Proは商用のプロプライエタリなセルフホスト型サーバーソフトウェア**です。セキュリティチームはクライアントのコードを読み、エンドポイント上で何をしているかを監査し、自分でビルドできます。これはリモートアクセスでは特に重要です。このソフトウェアにはマシンを完全に操作する権限が委ねられるため、規制対象の購入者は、ベンダーの説明をうのみにせず、クライアントの動作を自ら検証したいと考えるようになっています。

## メリット3：異なるサーバーライセンスモデル

RustDeskの標準プランは**ログインユーザー数と管理対象デバイス数**でライセンスされ、無制限の同時接続が含まれます。同時接続数を一定数でライセンスするのは[Customized V2](https://rustdesk.com/pricing#custom2)のみです。要件が変われば、いつでも[ライセンスをアップグレード](/ja/blog/upgrade-rustdesk-license-mid-subscription-ja)できます。

このモデルは環境の規模に合わせて拡張でき、[大規模フリートの計画ガイド](/ja/blog/rustdesk-scale-50000-200000-devices-ja)では最大20万台のデバイスまでの展開を取り上げています。Server Proはユーザー単位・デバイスグループ単位の[アクセス制御](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/permissions/)を追加し、BasicプランからはLDAP/OIDCによるSSOとカスタムクライアント生成も利用できます。

## RustDeskはISO 27001、SOC 2、HIPAAの要件にどう当てはまるか

企業の調達部門や医療分野のチームは、リモートアクセスツールがISO 27001、SOC 2、HIPAAにどう対応するかをほぼ必ず尋ねます。クラウド製品の場合は、ベンダー自身のインフラに対する認証と、その責任共有の条件に依存することになります。セルフホストのRustDeskはその逆です。ID/ランデブーサーバー、リレー、コンソールは自社のプログラムがすでにカバーしているインフラ上で動くため、自社のISO 27001の適用範囲、SOC 2の統制、HIPAAの保護措置の中で評価でき、その評価の一環としてセキュリティチームがクライアントのソースコードを確認することもできます。セルフホスティングは展開上の管理策であって認証ではなく、それを適用範囲に組み込むのは評価です。

実務上のポイントをいくつか挙げます。

- セルフホスティングでは、ランデブーサーバー、リレー、コンソール、保存される管理データの設置場所と運用者を自分で選べます。それらの場所とあわせて、エンドポイントの経路、バックアップ、管理者のアクセスも文書化してください。
- 調達要件としてベンダー側のSOC 2レポート、署名済みのBAA（Business Associate Agreement）、DPA、セキュリティ質問票への回答が必要な場合は、[sales@rustdesk.com](mailto:sales@rustdesk.com)のRustDeskチームに、お客様のケースで現在何を提供できるかをお問い合わせください。
- クライアントがオープンソースなので、「それが何をしているのか、どうやって確かめるのか」という問いには実際の検証で答えられます。ベンダーの保証レポートが答えるのは、調達における別の問いです。

つまり、セルフホスティングによってリモートアクセスを既存のコンプライアンスプログラムに組み込めます。規制対象のチームにとってこれは、検証できないインフラに対するベンダーの認証に頼るよりも、多くの場合強い立場です。

## セルフホスト型のGDPRプログラムを支えるコントロール

セルフホスティングは土台であり、その上でRustDeskは、セルフホストするチームがGDPR対応で頼りにする具体的なコントロールを提供します。

- **サーバーのデータは配置した場所にとどまり、外部への通信は限られた処理だけ。** セルフホストのID/ランデブーサーバー、リレー、Proの管理サービスは、展開データを稼働している場所で処理します。文書化すべき外部への通信は、Server Proのライセンス確認（1日に1回程度、rustdesk.comへのHTTPS）、カスタムクライアントのビルドサービス、クライアントの更新、外部メールサーバーを設定した場合のSMTP、そして接続する外部IDプロバイダーです。詳しくは[Server Proのオフライン・エアギャップ環境ガイド](/ja/blog/rustdesk-server-pro-offline-air-gapped-ja)をご覧ください。
- **監査ログの保持期間を設定できる。** [Server Proの監査ログ](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/audit-logs/)は、接続、ファイル転送、アラーム、コンソール操作を記録します。<strong>設定 > その他 > ログ保存期間（日）</strong>で`0`を指定するとすべてのログを無期限に保持し、正の値を指定するとそれより古いログが削除されます。クリーンアップは1時間に1回実行されます。エクスポートやバックアップの保持期間は別途定めてください。
- **きめ細かく範囲を限定したアクセス。** [アクセス制御](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/permissions/)は、ユーザー単位の割り当て、デバイスグループ、グループ間ルールによって、誰がどのデバイスに接続できるかを決めます（ユーザーグループとデバイスグループの権限は累積します）。共有アドレス帳はエントリーを整理するだけで、アクセスの境界ではありません。[コントロールロール](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/control-role/)は、技術者がセッション中にできること（キーボード／マウス、クリップボード、ファイル転送、音声、カメラ、ターミナル、印刷、録画など）を制限します。SSO/LDAPや被操作デバイスの2FAと組み合わせることで、最小権限と目的の限定を徹底できます。
- **プライバシーモードと接続ごとの同意確認。** 操作される側では受信する接続ごとに承認を求めることができ、プライバシーモード（WindowsとmacOSで対応）はセッション中にローカルの画面を暗転させて、画面上の個人データが意図せず見られることを防ぎます。
- **自社の裁量で削除できる。** データは自社サーバー上にあるため、ユーザーの無効化や削除、デバイスや記録の削除（REST API経由を含む）を行い、消去要求や保持に関する要求に直接対応できます。
- **リージョン内の自社運用インフラ。** ID/ランデブーサーバー、リレー、コンソール、保存データは、自社が管理するハードウェア上の、自分で決めた場所で動きます。
- **カスタムクライアントのビルドは一時的。** ブランド化したクライアントの生成は、RustDeskのビルドサービスを使う唯一の工程で、意図的に短期間で完結するようになっています。送信したビルド設定はビルド完了時に削除され、生成されたインストーラーも約1日後に自動で削除されるため、ダウンロードして自社の承認済みリポジトリで保管してください。

これらはGDPRプログラムで実際に使える手段です。文書化と運用は引き続き自社の役割ですが、データ主体からの要求への対応をベンダー任せにする必要はありません。

## 目に見える形で示せる主権

ランデブーサーバー、リレー、コンソール、保存データを自らホストすることで、コンプライアンスプログラムに具体的な拠り所が生まれます。自社が配置し、運用し、監査するインフラです。これはゴールではなく土台ですが、ほかのすべてがその上に成り立ちます。

## GDPRと主権のための導入チェックリスト

セルフホスティングは選択肢を与えてくれますが、その選択肢を実際のコントロールに変えるのは導入作業です。

- IDサーバー、リレー、コンソール、バックアップ、ログ、管理者の所在地を文書化する。
- 直接のピアツーピア経路とリレー経由の経路を分けて把握する。ドイツにあるサーバーを使っても、ドイツと他国の間の直接セッションがドイツ国内にとどまるわけではありません。
- 管理された場所を経由させることがピアツーピアの性能より重要な場合に、リレーを強制するかどうかを決める。
- デバイス、アカウント、監査、接続のメタデータについて、目的、保持期間、アクセスポリシーを記録する。
- 最小権限のデバイスグループ、利用可能な場合はMFA/SSO、技術者の入社・異動・退職に伴うアカウント管理プロセスを適用する。
- WebコンソールをHTTPSで保護し、管理用のネットワークアクセスを制限し、バックアップからの復元をテストする。
- ユースケースに応じて、処理活動の記録、処理者の審査、移転影響評価、DPIAなど、必要な法的評価を完了する。

RustDeskは主権を確保するアーキテクチャを支えられますが、そのアーキテクチャと法的根拠に対する責任は管理者に残ります。
