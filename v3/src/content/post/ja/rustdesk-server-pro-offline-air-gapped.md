いいえ。セルフホスト型のRustDesk Server Proは、完全なオフラインやエアギャップ環境で動かすようには設計されていません。Proのライセンスを有効に保つには、アクティベーションの時点だけでなく、サーバーの稼働中も継続して、アウトバウンドの接続でrustdesk.comに到達できる必要があります。そのため、完全に隔離されたネットワークはサポート対象のモデルから外れます。

## 結論から言うと

[ライセンス確認に関する公式FAQ](https://github.com/rustdesk/rustdesk/wiki/FAQ#how-often-does-pro-check-license)によると、検証は定期的に行われます。サーバーはほぼ1日1回、443番ポートでrustdesk.comに接続し、確認に失敗した場合は成功するか約7日が経過するまで再試行を続け、それを過ぎるとライセンスの検証が通らなくなります。この猶予期間があるため、短時間のインターネット障害ですぐに環境が止まることはありませんが、恒久的にオフラインのサーバーでは止まります。IDサーバーとリレーサーバーは引き続きセルフホストで、直接セッションはエンドポイント間を流れ、リレー経由のセッションは自社のリレーを使います。プロキシに対応しているため、必要なアウトバウンドのHTTPSの経路だけを許可し、それ以外のネットワークは閉じておけます。

## 詳しく

この要件が適用されるのは**Server Pro**です。<strong>RustDesk Server OSS（無料のコミュニティサーバー）</strong>にはライセンスの確認がありません。RustDeskのクライアントとServer OSSはAGPLライセンスで、Server Proは商用のプロプライエタリなセルフホスト型サーバーソフトウェアです。隔離したネットワークでも、クライアントとローカルのID/リレーサービスには、到達できる経路、正しい鍵、プラットフォームの権限が必要です。IDで確立した直接セッションはエンドポイント間を流れ、リレー経由のセッションは自社のサーバーを使います。クライアントに自社サーバーの公開鍵を設定すれば、IDベースのセッションはエンドツーエンドで暗号化されますが、[直接IPアクセスは暗号化されない](https://github.com/rustdesk/rustdesk/wiki/FAQ)ため、適切に設定したIDでの接続の代わりにはなりません。

もう一つ考慮すべきワークフローが**カスタムクライアントのビルド**です。Server Proでブランド化したクライアントや事前設定済みのクライアントを生成する場合、そのビルドはRustDeskのビルドサービスで実行されるため、ここでもアウトバウンドの通信が必要です。送信した設定はビルドの完了後に削除され、インストーラーは約1日後に自動で削除されるので、ダウンロードして自社のリポジトリに保管してください。

厳格なエアギャップのネットワークでは、ここが決定的なポイントです。rustdesk.comに*一切*到達できないサーバーは標準のモデルから外れるため、厳格なエアギャップの要件がある場合は、導入を決める前に具体的な状況をRustDeskに確認してください。はるかに多い「ほぼ隔離され、外向きの通信を厳しく絞った」構成であれば、rustdesk.comへのアウトバウンドHTTPSの経路を（直接またはプロキシ経由で）1本確保し、ファイアウォールのポリシーを書く前に、正確なドメイン、ポート、承認の手順を決めておきます。[RustDeskのドキュメント](https://rustdesk.com/docs/ja/)を参照してください。なお、同じライセンス要件があるため、[Dockerを使わずにインストールする場合でも、インターネットにまったく接続できない状態ではServer Proを動かせません](https://rustdesk.com/docs/ja/self-host/rustdesk-server-pro/installscript/)。

## 外部への依存をすべて洗い出す

閉ざされた環境を担当するセキュリティチームや[MSP](/ja/blog/rustdesk-for-msps-ja)は、RustDeskをインストールする前にこの点を確認するのが普通です。Server Proの外向きの通信のリストは短いものです。rustdesk.comへのHTTPSによるライセンスの検証、ブランド化したクライアントを生成する場合のカスタムクライアントのビルドサービス、クライアントのアップデート、メールサーバーがネットワークの外にある場合のSMTP、そして接続する外部IDプロバイダーです。ID/ランデブーサーバー、リレー、コンソールはネットワーク内で動くため、ネットワークを広く開ける代わりに、的を絞ったファイアウォールのルールで済みます。
