RustDeskは正規のオープンソースのリモートアクセスソフトウェアですが、正規のソフトウェアでも悪用されることはあります。詐欺師は被害者に電話をかけ、緊急の問題をでっち上げて、リモート操作ツールをインストールさせ、アクセスを許可するよう説得します。RustDeskもこのリスクと無縁ではなく、だまして得た同意を暗号化で正すことはできません。

そこで私たちは、その経路上の複数のポイントに警告と「手間」を設けてきました。ウェブサイト、Androidの被制御デバイス側のフロー、主要な配布チャネル、そしてパブリックサーバーです。これらの対策は、正規のユーザーにも不便をもたらします。本記事では、私たちが何を行い、なぜそうしたのか、そしてどこに限界が残るのかを説明します。

## RustDeskはリモートアクセス詐欺に対して何をしてきたのか？

| 対策                                     | 対応する問題                                                     | コストや限界                                                           |
| ---------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| ウェブサイトとクライアントでの警告表示   | 見知らぬ相手からRustDeskのインストールを指示されている人         | 警告は無視される可能性がある                                           |
| Google Playからの自主的な撤退            | なじみのあるアプリストアを使った、詐欺目的の手軽なインストール   | 正規のAndroidユーザーはストアでの見つけやすさとPlayの自動更新を失う    |
| パブリックサーバーでのログイン要件       | 共有インフラを匿名で悪用する詐欺やボットネット                   | 正規ユーザーもサインインが必要になり、一部の既存ワークフローが妨げられる |
| 被制御デバイスのセキュリティ設定         | パスワードの盗難、広すぎるネットワーク露出、無人アクセスのリスク | 正しく設定する必要があり、本人が自ら情報を明かすことまでは防げない     |

これらはリスクを減らすための対策であり、RustDeskが詐欺に対して万全だと主張するものではありません。

## 被害者になり得る人の目に触れる場所での警告

[RustDeskのサポートページ](https://rustdesk.com/support)の冒頭には、詐欺に関する直接的な警告を掲載しています。知らない相手、信頼できない相手と電話をしながらRustDeskのインストールを求められている人に、そこで手を止めるよう呼びかけるものです。[RustDeskのGitHubリポジトリ](https://github.com/rustdesk/rustdesk)にも、不正アクセス、不正操作、プライバシー侵害への悪用を禁じる免責事項を記載しています。

警告は、[GitHubリリース](https://github.com/rustdesk/rustdesk/releases)で配布している公式Androidクライアントにも組み込まれています。被制御側となるログイン前のAndroidデバイスで**サービスを開始**をタップすると、画面キャプチャサービスが始まる前に警告が表示されます。この警告は、知らない相手や信頼できない相手の指示で操作しているユーザーに、作業をやめて電話を切るよう伝えます。公式ビルドでは、先に進めるようになるまでカウントダウンが入ります。[現在の被制御側のフロー](https://github.com/rustdesk/rustdesk/blob/6c578292e8ebbbec708b76986ba8c4bc7c509747/flutter/lib/mobile/pages/server_page.dart#L244-L421)と[英語版の警告文](https://github.com/rustdesk/rustdesk/blob/6c578292e8ebbbec708b76986ba8c4bc7c509747/src/lang/en.rs#L192-L194)は、どちらもオープンソースのリポジトリで確認できます。

この配置には意味があります。一般的なセキュリティページは製品を調べている人にしか届きませんが、**サービスを開始**の時点で出る警告は、Androidへの着信セッションがまさに可能になろうとしている瞬間に、その本人へ届きます。それでも、説得力のある相手を疑うよう本人に強制することはできません。

## RustDeskがGoogle Playにない理由

2023年9月3日、RustDesk公式のXアカウントは[「ユーザーを狙ったさらなる詐欺を防ぐため、RustDeskを一時的にGoogle Playから公開停止しました」](https://x.com/rustdesk/status/1698372220379349421)と発表しました。このリンクと投稿内容は回答済みの[GitHub Discussion #5660](https://github.com/rustdesk/rustdesk/discussions/5660)にも残っており、現在のRustDeskの[FAQにも、詐欺を理由にプロジェクトが自らGoogle Playから撤退したと記載されています](https://github.com/rustdesk/rustdesk/wiki/FAQ#apple--google-store)。

そのため、RustDeskは**現在Google Playでは配布されていません**。これは、Androidクライアントがマルウェアだという意味でも、インストールした人が全員危険にさらされているという意味でもありません。詐欺の指示でよく使われる経路を一つ減らすための、配布方法に関する判断でした。

トレードオフは確かにあります。Google Playから離れたことで、正規ユーザーにとっての見つけやすさ、なじみのあるインストール方法、ストアによる自動更新が失われました。現在のAndroidビルドは、[RustDesk公式のGitHubリリース](https://github.com/rustdesk/rustdesk/releases)と[F-Droid](https://f-droid.org/packages/com.carriez.flutter_hbb/)から入手できます。ダウンロード先は必ず自分で確かめてください。突然連絡してきたサポート担当者を名乗る相手から送られたリンクで、APKをインストールしてはいけません。[RustDeskのAndroid・iOSリモートコントロールのガイド](/ja/blog/rustdesk-remote-control-android-ios-ja)に、現在のモバイル機能と入手元をまとめています。

## パブリックサーバーでログインが必要な理由

RustDeskの現行の[パブリックサーバーのログインに関するガイド](https://github.com/rustdesk/rustdesk/wiki/Login-required-for-public-server)では、詐欺やボットネットによる悪用が続いているため、制御側（コントローラー）のログインを必須にしていると説明しています。ログインは無料で、GoogleやGitHubなど対応するサードパーティのIDプロバイダーを使います。パブリックサーバー独自のユーザー名とパスワードは用意していません。ガイドによると、現時点でログインが必要なのはコントローラー側だけです。

これにより本人確認のステップが一つ加わり、RustDeskがデモと検証のために運用しているインフラへの匿名アクセスの一部がなくなります。プライベートなRustDeskサーバーには適用されず、ほかのインフラを使ったり新しいIDを用意したりする詐欺師を止めることもできません。

この変更は混乱も招きました。[新しいログインエラーに関するRedditの議論](https://www.reddit.com/r/rustdesk/comments/1sm91xv/getting_this_error_when_trying_to_connect_anyone/)では、ログイン手順を理解して完了するまで、自宅や家族のデバイスに接続できなかったという正規ユーザーの報告がありました。サードパーティのIDと連携すること自体に反対する声もありました。これらのコメントは、この制限が詐欺師に効くかどうかの証拠にはなりませんが、運用上のコストは確かに示しています。手間を増やす悪用対策は、そのコストを率直に認めるべきです。

## RustDeskの被制御デバイスはどう保護すればよいのか？

プラットフォーム側の制限は、防御の一層にすぎません。被制御デバイスの所有者や管理者も、誰が接続できるか、盗まれた認証情報で何ができてしまうかを絞り込むべきです。

### 1. 強力で使い回しのない固定パスワードを設定する

[無人アクセス](/ja/blog/rustdesk-unattended-access-setup-ja)を使う場合は、被制御デバイスのRustDeskのセキュリティ設定で、**強力で使い回しのない固定パスワード**を設定してください。OSのログインパスワード、メールのパスワード、ほかのサービスで使っているパスワードは流用しないでください。漏れた可能性があれば、すぐに変更してください。

有人サポートでは、可能であればワンタイムパスワードか、クリックによる明示的な承認を優先してください。強力な固定パスワードは、推測、クレデンシャルスタッフィング、パスワードの使い回しによるリスクを減らします。しかし、被害者がそのパスワードを電話の相手に読み上げてしまえば役に立ちません。

### 2. 被制御デバイスで2FAを有効にする

RustDeskには、被制御デバイスへの着信接続に対するTOTP方式の2FAがあります。接続を受け入れる側のデバイスでセキュリティ設定を開き、<strong>二要素認証（2FA）</strong>を有効にして、認証アプリでQRコードを読み取り、表示された6桁のコードで設定を確定します。

有効にすると、通常の接続パスワードだけでは接続できなくなります。被制御デバイスがセッションを許可する前に、コントローラー側は現在の6桁のTOTPコードも入力する必要があります。この機能はもともと[無人アクセス向けの2FA](https://github.com/rustdesk/rustdesk/commit/44e6b7dbb0125dc0c288c19a16a944b5d605852b)として導入されたもので、[TOTPの実装は公開されています](https://github.com/rustdesk/rustdesk/blob/master/src/auth_2fa.rs)。

RustDeskでは、コントローラーのデバイスを承認済みデバイスとして登録し、以降の2FAの確認を省略することもできます。最も厳格に運用するなら、この省略機能は無効のままにしてください。使う場合は承認済みデバイスの一覧を見直し、紛失・交換・共有されたデバイスや、もう許可すべきでないデバイスを削除してください。

2FAは、推測された、使い回された、あるいは漏えいしたパスワードから守ってくれます。しかし、パスワードと現在の認証コードの両方を詐欺師に渡してしまう人は守れません。

### 3. IP許可リストで着信接続を制限する

RustDeskの画面では、この機能は「IP ホワイトリスト」（英語版の表記はIP Whitelisting）と表示されます。役割としてはIP許可リストで、被制御デバイスは、パスワードと2FAによる認証より前に、送信元アドレスがリストにない接続を拒否します。

設定場所は次のとおりです。

- **デスクトップの被制御デバイス：** **設定 → セキュリティ → セキュリティ → IP ホワイトリストを使用する**
- **モバイルの被制御デバイス：** **設定 → 画面を共有 → IP ホワイトリストを使用する**

この設定には、個々のIPv4・IPv6アドレスとCIDR範囲を指定できます。CIDRは、ネットワークアドレスとプレフィックス長を組み合わせた表記です。プレフィックス長は先頭から何ビットを固定するかを表し、値が大きいほど許可される範囲は狭くなります。

- `203.0.113.10` または `203.0.113.10/32`：IPv4アドレス1つ。
- `203.0.113.0/24`：`203.0.113.0`から`203.0.113.255`までの256個のIPv4アドレス。
- `2001:db8::10/128`：IPv6アドレス1つ。
- `2001:db8:1234::/64`：IPv6サブネット1つ。

これらはドキュメント用に予約された例示用の範囲なので、そのままコピーしないでください。実際のコントローラーのアドレスやネットワークを入力します。複数のエントリは、カンマ、セミコロン、スペース、改行で区切れます。この設定は[クライアントの高度な設定リファレンス](https://rustdesk.com/docs/ja/self-host/client-configuration/advanced-settings/#whitelist)に記載されており、[被制御側での適用処理はソースコードで確認できます](https://github.com/rustdesk/rustdesk/blob/1.5.0/src/server/connection.rs#L1410-L1437)。

範囲は実用上できるだけ狭くしてください。オフィスの固定の送信元アドレスや既知のVPNの範囲は良い候補です。家庭用回線の動的アドレスや、移動しながら使うコントローラーには向きません。自社のNAT、VPN、直接接続、リレーの構成で、RustDeskがどの送信元アドレスを認識するかを確認し、作業中のセッションを閉じる前に、別のセッションから新しいルールを検証してください。アドレスやCIDRを間違えると、正規のサポート担当者が締め出されてしまいます。

許可リストは、接続元になり得る場所を絞り込むものです。パスワードや2FAの代わりにはならず、すでに許可されたネットワークから操作している悪意のあるコントローラーは止められません。

### 4. 接続できるRustDesk IDを制限する

RustDesk 1.5.0以降では、被制御デバイスがリストに登録したRustDesk IDからの接続だけを受け入れるようにもできます。画面上の表記は「ID ホワイトリスト」（英語版はID whitelisting）です。ネットワークアドレスは変わるものの、制御に使うデバイスは決まっていて、IP許可リストでは運用しづらいサポートチームに向いています。

設定場所は次のとおりです。

- **デスクトップの被制御デバイス：** **設定 → セキュリティ → セキュリティ → ID ホワイトリストを使用する**
- **モバイルの被制御デバイス：** **設定 → 画面を共有 → ID ホワイトリストを使用する**

このデバイスの操作を許可するデバイスのRustDesk IDを入力します。IPのリストと同じく、複数のエントリはカンマ、セミコロン、スペース、改行で区切れます。照合では大文字と小文字を区別せず、2種類のワイルドカードが使えます。

- `123456789`：IDを1つ指定。
- `12345678?`：`?`はちょうど1文字に一致するため、`12345678`で始まる9文字のIDをすべて許可します。
- `support-*`：`*`は任意の数の文字に一致します。共通の接頭辞を持つカスタムIDをコントローラーで使っている場合に便利です。

これらも例として示した値です。この設定は[クライアントの高度な設定リファレンス](https://rustdesk.com/docs/ja/self-host/client-configuration/advanced-settings/#id-whitelist)に`id-whitelist`として記載されているため、管理者はカスタムクライアントにあらかじめ組み込んでおけます。[適用処理はソースコードで確認できます](https://github.com/rustdesk/rustdesk/blob/1.5.0/src/server/connection.rs#L1439-L1467)。

このチェックは、コントローラーがログイン要求を送った時点で、パスワードや2FAコードの確認より前に行われます。また、通常はパスワードが不要な、セッション中の双方の役割の入れ替えにも適用されます。IP許可リストも設定している場合、接続は両方のチェックを通過しなければなりません。拒否されたコントローラーには「あなたの ID は接続先によってブロックされています」と表示され、試行にはレート制限がかかるため、許可されたIDを短時間で探り当てることはできません。

限界も理解しておいてください。IDは接続してくるクライアントが自己申告するものです。本人であることの証明にはならず、改変されたクライアントなら許可されたIDを名乗れます。RustDeskはこの注意書きを設定項目の横に表示しています。このリストの役割は、リストにないIDを持つ通常のクライアントを、パスワードの入力画面に進む前に拒否することです。管理者があらかじめリストを設定したデバイスなら、電話の相手がユーザーを言いくるめてIDとパスワードを読み上げさせても、標準のクライアントではリストにないIDから接続できません。強力なパスワードと2FAは引き続き有効にしておき、作業中のセッションを閉じる前に、別のセッションからリストを検証してください。入力ミスがあると、正規のサポート担当者が締め出されてしまいます。

## これらの対策でもできないこと

警告表示、ストアからの撤退、ログイン要件、強力なパスワード、2FA、IP・IDの許可リストは、それぞれ攻撃者の機会を少しずつ奪います。しかし、ソーシャルエンジニアリングという根本的なリスクを取り除けるものはありません。人は今後も、アクセスを承認したり、すべての認証要素を明かしたりするよう説得されてしまう可能性があります。

セルフホストしても、悪用が不可能になるわけではありません。組織は自社のRustDeskサーバーとポリシーを管理できるようになりますが、詐欺師もプライベートなインフラを運用したり、改変したクライアントを配布したりできます。RustDeskのパブリックサーバーの制限が適用されるのはパブリックサーバーだけで、セルフホスト環境はその運用者が定めたポリシーのもとで動作します。

知らない相手からRustDeskのインストール、サービスの開始、パスワードの共有、2FAコードの開示、ネットバンキングのサイトを開くことを求められたら、そこで手を止めてください。特定のベンダーに偏らない私たちのガイド「[リモートデスクトップ詐欺の見分け方と回避策](/ja/blog/avoid-remote-desktop-scams-ja)」では、警戒すべき兆候と、すでにアクセスを許してしまった場合の対処法を説明しています。
