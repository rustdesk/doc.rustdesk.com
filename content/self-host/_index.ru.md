Собственный сервер RustDesk позволяет самостоятельно управлять инфраструктурой сервера ID и ретранслятора, хранить данные развёртывания на своих системах и настраивать удалённый доступ под требования вашей сети и нормативные требования.

Поддержка доступна в нашем [Discord](https://discord.com/invite/nDceKgxnkV) для OSS и по [электронной почте](mailto:support@rustdesk.com) для Pro.

## Какой сервер RustDesk выбрать?

| Вариант | Кому подходит | Что вы получаете |
| --- | --- | --- |
| [RustDesk Server OSS](/docs/ru/self-host/rustdesk-server-oss/) | Частным лицам и командам, которым нужен бесплатный серверный компонент с открытым исходным кодом | `hbbs` и `hbbr`, поддержка сообщества, развёртывание и настройка вручную |
| [RustDesk Server Pro](/docs/ru/self-host/rustdesk-server-pro/) | Компаниям, которым нужны централизованное администрирование и корпоративные функции | Веб-консоль, API, OIDC, LDAP, 2FA, управление устройствами, контроль доступа и управление несколькими ретрансляторами |

## Как работает собственный сервер? {#how-does-self-hosted-server-work}

Технически это два исполняемых файла (сервера):

- `hbbs` — сервер ID RustDesk (рандеву / сигнальный сервер), слушает TCP (`21114` — для http, только в Pro, `21115`, `21116`, `21118` — для WebSocket) и UDP (`21116`)
- `hbbr` — ретранслятор RustDesk, слушает TCP (`21117`, `21119` — для WebSocket)

При установке с помощью сценария установки, docker compose или deb-пакета устанавливаются обе службы.

Вот [иллюстрации](https://github.com/rustdesk/rustdesk/wiki/How-does-RustDesk-work%3F) того, как клиент RustDesk взаимодействует с `hbbr` / `hbbs`.

Пока RustDesk запущен на компьютере, тот постоянно отправляет запросы серверу ID (`hbbs`), сообщая свои текущие IP-адрес и порт.

Когда вы подключаетесь с компьютера A к компьютеру B, компьютер A обращается к серверу ID и запрашивает связь с компьютером B.

Затем сервер ID пытается соединить A и B напрямую с помощью пробивки NAT (hole punching).

Если пробить NAT не удаётся, A связывается с B через ретранслятор (`hbbr`).

В большинстве случаев пробивка NAT срабатывает, и ретранслятор не используется вовсе.

Вот обсуждение на тему [стоит ли разворачивать собственный сервер RustDesk?](https://www.reddit.com/r/rustdesk/comments/1cr8kfv/should_you_selfhost_a_rustdesk_server/) (на английском языке)

## Необходимые порты

Какие порты нужны для собственного сервера RustDesk, во многом зависит от вашего окружения и того, как вы используете RustDesk. В примерах по всей документации обычно предлагается открыть все порты.

Основные порты: \
TCP `21114-21119` \
UDP `21116`

- TCP `21114`: HTTP API-сервер в RustDesk Server Pro.
- TCP `21115`: проверка типа NAT.
- UDP `21116`: регистрация устройств.
- TCP `21116`: регистрация устройств и пробивка NAT.
- TCP `21117`: передача данных через ретранслятор.
- TCP `21118`: соединения WebSocket.
- TCP `21119`: соединения WebSocket.

Порты `21115`-`21117` — минимум, необходимый для работы RustDesk. Они отвечают за сигнализацию, ретрансляцию и прохождение NAT.

При настройке WSS порты TCP `21118` и TCP `21119` обычно не нужно открывать наружу, потому что к ним обращается обратный прокси, например Nginx, изнутри сети. Если вы не используете WebSocket, открывать эти порты не нужно. См. этот [пример конфигурации Nginx](/docs/ru/self-host/rustdesk-server-pro/faq/#8-add-websocket-secure-wss-support-for-the-id-server-and-relay-server-to-enable-secure-communication-for-all-platforms).

Пользователям Pro без SSL-прокси нужно открыть порт TCP `21114`, чтобы работал API. Если на сервере настроен HTTPS (`443`), открывать TCP `21114` в интернет не нужно.

RustDesk также поддерживает режим, в котором открыт только TCP `443`, а все остальные порты закрыты. В такой конфигурации связь возможна только через ретрансляцию по WSS, а прямые P2P-соединения недоступны.
